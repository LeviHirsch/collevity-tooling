Nothing today defines what a directed note is addressed to. The 2026-08-12 design never reached it; the 8/11 run faked the recipient inside one session. Substrate already exists: the live capture hook writes session_id, cwd, and kind (claude-session/grok-session) per prompt to the lake. Settle the address space before T1 fixes a record shape.

Decided 2026-08-15: cwd-selected, id-resolved. Sender picks by project directory; the stored note carries the resolved session_id plus the cwd it was chosen by. Remaining work: the resolver, and the tiebreak when two live sessions share a cwd.

Decision (2026-08-16): three address-space calls, all resolved with Levi.

1. Liveness — no filter. Every registered session stays resolvable, ranked by most-recent registration. The roster has no SessionEnd hook, so "live" is unknowable; and T16 (drain at session start) means a note to a dormant session is delivered when it wakes, not lost. Staleness policy stays out of T6.
2. Tiebreak — newest wins, ambiguity surfaced. resolve() returns the most recently registered match plus the full candidate list, so T3 can warn or offer a pick. Never blocks, never hides that a choice existed.
3. cwd match — normalized realpath exact first, else nearest-ancestor. An address of a repo root matches a session in a subdir when nothing matches exactly; dev worktrees nest sessions too deep for exact-only to be usable.

Shipped (2026-08-16): bin/mailman_resolve.py turns a project directory into a recipient session_id off the T13 roster, with 23 tests (41 total green). Exact-match short-circuits; only when nothing sits exactly at the address do sessions below it match, nearest first. No liveness filter and newest-wins-on-tie, both per the decisions recorded above; resolve() hands back the whole candidate list beside the pick so T3 can surface a tie rather than have one hidden from it. Diverged from the task title in one way worth naming: it exposes candidates() alongside resolve(), because 'one session_id out' cannot honestly represent an ambiguous cwd. Also added AGENTS.md - the repo had none, and the hook-vs-module split (hooks must exit 0 and stay silent, this module deliberately may not) is not inferable from any single file. Knowingly left out: the reverse match direction (an address BELOW a session's cwd reaching that session) is unimplemented and tested as a non-match, since it was not decided; and no retention/pruning of stale roster lines.

Decision (2026-08-16, Levi) — supersedes the address model above.

1. Recipients are live sessions only. A note sent to a session that has been closed fails immediately ("nobody there") rather than queueing for that session to reopen. Nothing currently reports a session ending, so liveness needs a mechanism that does not exist yet.
2. The project folder is not the recipient's name. Two sessions running in one folder can serve entirely different purposes, so a folder cannot identify one of them. Folder-as-address was a bad self-constraint. Separate the human-facing name from the session id.
3. Routing is global across the user's live sessions, with optional Collevity environment scoping later. The intent is sharing context between whatever scopes the user is working in. A folder is at most a filter for narrowing a list of live sessions.

Consequence: cwd-selected/id-resolved (2026-08-15) is superseded. The no-liveness-filter and newest-wins-tiebreak calls (2026-08-16) are void — the tie existed only because the folder was the name. PR #3 is not merged; changes requested. Next open question: what a sender types to name a recipient, given the name is no longer the folder.

Levi's specification, already given: each live session keeps a small published view of itself in the shared cache and updates it as it goes. A session's per-turn check asks 'do I need to update myself to any other context' and reads those published views. Haiku is the switchboard operator making the relevance call. Recipient selection therefore happens by reading published views - NOT by folder, NOT by an assigned name, NOT by subscription to a subject. The earlier 'separate the name from the session id' note is void: there is no name to assign, and the open question it left ('what a sender types to name a recipient') is not a real question.

Consequences: the folder-to-session lookup in PR #3 is not the addressing mechanism and almost none of it survives. The missing piece is the published self-view, now T18. Liveness needs no new machinery - a session that stopped updating its view is a session that stopped - which is what makes the fail-immediately ruling implementable.
