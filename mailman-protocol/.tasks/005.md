Haiku is an add-on over the base case, not critical path: explicit send (T3) is the base case that must work without it. This is a layer to run and learn from.

Haiku selects a recipient by reading the published session views (T18) and calls the T3 send path. It sees views only - the sender's own and the candidates' - never transcript content.

Decision (2026-08-17, Levi): switchboard, not reader. The fork was whether Haiku matches self-reported views (switchboard) or reads the sender's raw turn content to notice relevance no agent flagged (reader). Switchboard because: it does not reverse T18's ruling keeping LLMs off the prompt path; its failure mode is a misrouted note rather than an LLM over raw transcript, which is adjacent to the README's ban on moving transcript between sessions; entry-router's address scheme is unratified by its own note and reader would make mailman depend on it; and reader costs a Haiku call per turn where switchboard fires only on view-update.

This supersedes the task's original question ("what may Haiku see", phrased against org node paths, which this project does not have). T18's view is the mailman-native directory face, so that framing is answered by construction rather than re-grounded.

Open, deliberately NOT resolved: switchboard cannot deliver the "Haiku writing it is the high-leverage path" claim in README Settled - the leverage there was the noticing, which a view-matcher cannot do by construction. Left as a live tension to be answered empirically by running this, not edited out of Settled. If reader returns, its likely shape is views plus the sender's own recent turns, never the recipient's.

Reconciliation with entry-router (02_CONTENT/entry-router/) is a non-issue under switchboard - no content reading, no competing pipeline. It returns only if reader does.

README's Open item 1 and the matching "do not implement the Haiku writer" line are stale once this lands; fold that in.
