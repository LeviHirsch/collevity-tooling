## AC3.2 — oat never on stdout / never in parent env / never in shell history
**Verdict:** PASS
**Evidence:** `build_child_env` (`cas/run.py:76-86`) returns a fresh dict and never assigns into `os.environ`, so the parent process env is untouched — confirmed structurally and by `tests/test_phase3.py:110-116` (`test_oat_never_enters_parent_env`). The identity echo at `cas/run.py:228` only prints `label` and `record.email`, never `record.oat`; `cas/io.py:46-49` routes `notice()` to stderr, not stdout. The only place that writes the oat at all is into the child's env dict handed to `Popen` (`cas/run.py:161`, `_real_launcher`); cas's own stdout pass-through (`_pump_and_capture`, `cas/run.py:125-147`) only relays the **child's** stdout bytes, never anything cas itself constructs from the oat. Test `tests/test_phase3.py:119-124` (`test_oat_never_printed_to_any_stream`) asserts the oat string never appears in anything shown via the `IO` surface. Shell-history avoidance is a consequence of the design rather than a directly tested property: the CLI invocation is `cas run <label> -- <cmd…>` (`cas/cli.py:33-47`) — the oat is never typed/echoed into a shell command (no `export TOKEN=...` pattern), so there is no command-line text containing the secret for a shell to log.
**Reason:** oat only ever lands in a Popen-bound child env dict; never assigned to `os.environ`, never printed, and never appears in any user-typed/echoed command — matches the env-injection (not export) pattern the AC requires.

**Reason:** no shared mutable state between invocations; each child env is a freshly constructed dict scoped to that call only — verified by a same-process two-invocation test.

## AC3.6 — child stderr surfaced unmodified + best-effort auth guidance
**Verdict:** PASS
**Evidence:** `_real_launcher` (`cas/run.py:150-188`) always inherits stderr (no `popen_kwargs["stderr"]` override is ever set, so it defaults to the parent's stderr — child writes go straight through unmodified). stdout handling is TTY-aware: if `sys.stdout.isatty()` (`cas/run.py:156`) stdout is also inherited untouched (`cas/run.py:177-179`); otherwise it is piped and teed via `_pump_and_capture` (`cas/run.py:125-147`), which writes every chunk through verbatim (`cas/run.py:139-140`) while retaining only a bounded tail (`_TAIL_MAX = 64*1024`, `cas/run.py:51`) for scanning — this matches the documented design decision (`cas/run.py:14-22`) that the dead-token 401 signal was observed on stdout, not stderr, against CLI v2.1.197. The matcher `looks_like_auth_failure` (`cas/run.py:89-109`) is conservative: exact phrase matches (`"invalid bearer token"`, `"failed to authenticate"`, `"authentication_error"`) plus a co-occurrence rule requiring `"401"` alongside an auth-related word, avoiding false positives on a bare "401" in unrelated output. Guidance is only printed when `returncode != 0 and captured and looks_like_auth_failure(captured)` (`cas/run.py:241-245`), pointing to `cas rm <label>` then `cas add`, with no automatic revocation/re-mint anywhere in the module. Tests: `tests/test_phase3.py:200-210` (`test_auth_failure_signal_triggers_remint_guidance`, scripted with the real CLI v2.1.197 probe string), `tests/test_phase3.py:213-220` (`test_nonzero_exit_without_auth_signal_prints_no_guidance`), `tests/test_phase3.py:223-230` (clean exit → no guidance), `tests/test_phase3.py:248-259` (matcher exact-match and conservative-negative cases).
**Reason:** stderr inheritance is unconditional and unmodified; the stdout-tee + conservative matcher correctly implements the documented v2.1.197 finding as a best-effort, non-blocking guidance layer with no auto-remediation.
