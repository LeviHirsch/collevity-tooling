# Ontologist Review — Revision 2 (2026-06-26)

## 1. Essence

The goal statement remains precise: decouple account authorization from the browser session as a portable per-process artifact. AC2.2's Chrome-profile routing is correctly scoped as a mint-time convenience, not a mechanism change — the credential primitive is still the oat, and the account-correctness guarantee still lives in AC2.3 + AC2.6. No essence drift.

## 2. Root cause

No new symptoms-vs-root-need concern introduced by Rev 2. The Chrome-profile routing addresses a genuine sub-problem (which cookie jar does the OAuth URL land in) and keeps correctness in the consent-page display rather than inferring it from profile identity. Sound.

## 3. Prerequisites

AC2.2 states the tool "brings that profile's window to the front, then opens the URL in it." This conflates mechanism with outcome. On macOS, `open <url>` routes through Chrome's URL handler, which may open in the most-recently-active window regardless of which window was focused. Whether focus-then-open reliably lands the URL in the selected profile's cookie jar is an unverified implementation assumption — yet the AC states it as a behavioral guarantee ("opens the URL in it"). If the assumption fails, the profile-selection step is cosmetic: the user picks a profile, but the URL opens in a different one.

DEC-011 names this "window-focus-then-open" without verifying the outcome. AC3.6's best-effort framing (dead-token detection) shows the spec knows how to hedge unverified behaviors; AC2.2 needs the same epistemic treatment.

## 4. Hidden assumptions

**mint_profile dual-presence (AC2.2 ↔ AC2.7):** AC2.2 says "the selected profile is recorded in the record's `mint_profile` field." AC2.7 says "`mint_profile` populated only if a Chrome profile was selected at AC2.2." The behavioral claim (recording happens) appears in AC2.2; the actual store-write belongs to AC2.7. A tester reading AC2.2 in isolation cannot determine whether its test must verify the write or only the selection interaction — this blurs the mutual-exclusivity boundary between the two ACs. Fix: remove the "recorded in `mint_profile`" clause from AC2.2; let AC2.7 own the store-write claim in full.

## 5. Phase ordering

No forward-dependency violations. `mint_profile` enters the schema in Phase 1 (AC1.4), is selected in Phase 2 (AC2.2), and is written in Phase 2 (AC2.7). Ordering is clean.

---

**Most load-bearing concern:** AC2.2 makes a behavioral guarantee ("opens the URL in [the selected profile]") that rests on an unverified macOS/Chrome routing mechanism — the same category of unverified-stdout assumption that prompted DEC-010's verification spike. If focus-then-open doesn't land the URL in the chosen cookie jar, the profile-selection UX misleads the user about which account context they're authorizing against, silently undermining the mint-time correctness the whole trust model depends on.
