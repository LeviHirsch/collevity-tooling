## AC4.2 — match `claude auth status` (default config dir) email against stored records
**Verdict:** UNCLEAR
**Evidence:** `default_login_email` (`cas/listing.py:118-140`) runs `[claude_bin, "auth", "status"]` with `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` stripped from the child env (`cas/listing.py:127-129`), matching the AC's "default config dir, no special env" requirement. `run_list` (`cas/listing.py:163-170`) lowercases/strips both the probe result and each stored `rec.email` before comparing, marks matching labels active, and appends "(no active interactive login matched)" when there is no match (`cas/listing.py:173-175`). `parse_login_email` (`cas/listing.py:74-86`) prefers a `"email": "..."` / `email=...` field match via `_EMAIL_FIELD_RE` (`cas/listing.py:45`) and falls back to the first bare email-shaped substring via `_EMAIL_ANY_RE` (`cas/listing.py:46`) — tolerant of both JSON-ish and human-readable formats, never raises, returns `None` on no match. Tests cover the wiring: `tests/test_phase4.py:108-126` (active row marked), `:128-140` (no-match note), `:142-149` (probe returns `None`), `:151-163` (case-insensitive match), `:165-179` (multiple rows sharing one email), `:181-187` (`parse_login_email` prefers the `email` field), `:189-211` (env-stripping verified against a mocked subprocess).
However: nothing in the test suite or codebase exercises `parse_login_email`/`default_login_email` against a captured sample of REAL `claude auth status` stdout — all tests construct synthetic strings (e.g. `tests/test_phase4.py:181-187`, `:189-211` mock `subprocess.run` directly). The docstring at `cas/listing.py:75-79` itself states the parser is "deliberately tolerant" and "Tolerant of JSON or human formatting" without citing a DEC/verification note (contrast with `cas/switch.py:5` and `cas/run.py`'s AC3.6 which cite DEC-010/an observed v2.1.197 string). If real `claude auth status` output does not contain a bare `email` field/value in the format assumed by `_EMAIL_FIELD_RE`/`_EMAIL_ANY_RE` (e.g., if it never prints the email at all outside of a login/profile display, or embeds it differently), the match silently degrades to "no match" for every row — a functioning-but-useless AC4.2 that no test would catch, since all tests supply the assumed format themselves.
**Reason:** implementation and test coverage of the match logic itself is solid, but the logic rests on an unverified assumption about real `claude auth status` output format, so whether AC4.2 actually works against the live CLI is unconfirmed — flagged UNCLEAR per the orchestrator's specific ask.

## AC5.1 — `use <label>` invokes `claude auth login --email <stored-email>`
**Verdict:** PASS
**Evidence:** `run_use` (`cas/switch.py:44-92`) builds `cmd = [claude_bin, "auth", "login", "--email", record.email]` (`cas/switch.py:86`) and dispatches it via the injected `launcher` (`cas/switch.py:88`), with `_real_login` (`cas/switch.py:39-41`) running it via `subprocess.run(list(cmd))` inheriting stdio for a fully interactive native reauth. Test `tests/test_phase4.py:256-264` (`test_use_invokes_auth_login_with_stored_email`) asserts the exact argv.
**Orchestrator flag 1 — the second `io.notice` call:** `run_use` emits two `io.notice(...)` calls before launching (`cas/switch.py:78-82`): the first echoes `"switching to {label} ({record.email})"`, the second adds `"on the consent page, confirm it shows {record.email} before approving — the browser may be logged into a different account."` This second call is an additional reminder beyond the bare text of AC5.1 (AC5.1 only requires invoking `claude auth login --email <stored-email>` and letting the user complete reauth natively) — it does not gate, block, or alter the `launcher(cmd)` call that follows at `cas/switch.py:88`, so it does not interfere with or weaken AC5.1's requirement. It mirrors the AC2.3 consent-page-check pattern from `add` (as the module docstring at `cas/switch.py:10-14` explains) and is consistent with the spec's overall "right-account verification built in" success criterion, though AC5 itself does not mandate it. Both notices route to stderr via `io.notice` (confirmed by `ConsoleIO` used elsewhere), so they do not contaminate anything `claude auth login` itself writes to stdout. Test `tests/test_phase4.py:266-274` (`test_use_echoes_identity_and_consent_reminder`) covers both lines.
**Reason:** the core AC5.1 invocation is present and tested; the extra consent-page reminder is additive UX, not a blocker or deviation, so AC5.1 is satisfied regardless of it.
