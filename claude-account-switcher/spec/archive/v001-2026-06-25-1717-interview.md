## Ingested LOCKED context (not re-litigated)

- **Objective.** Run multiple Claude accounts on one machine *truly concurrently*, with the right
  account guaranteed in each slot, where authorization is an explicit, portable artifact — not a
  side effect of which account the browser is logged into.
- **Concurrency includes the SDK.** Launching SDK agents under different accounts simultaneously.
  Mechanism must be env/process-scoped (works for interactive session and spawned SDK process alike).
- **Design spine:** slot/concurrency primitive = `CLAUDE_CONFIG_DIR` (per-process, empirically
  proven). Credential primitive = authorize once, capture portable token, plant into named slot;
  browser touched only at one-time mint. Public single-credential switchers are mutually exclusive,
  explicitly NOT our model.
- **Right-account verification is a deliverable** (`claude auth status` email match + guidance +
  error-checking).
- **Browser decoupling is a hard constraint.** After mint, nothing reads the browser session.
  Incognito preferred at mint.
- **Distribution:** private workshop in monorepo → export to a clean public repo
  `claude-account-switcher`. `deliverables/` is staging only.
- **Out of scope now:** team-provisioning / check-in auto-bind layer. Levi mints/holds accounts;
  teammates receive them. Future iteration.
- **Verified facts** in `GROUND-TRUTH.md` (CLI v2.1.191). Corrections carried: no `claude`
  incognito flag; isolation is per-process not per-keystroke.

### Constraints / non-negotiables to carry into ACs
- True concurrency (two processes, two accounts, no token hijack).
- Zero shell disruption (no PID-scanning wrapper, no forced sub-shell, no killing live sessions).
- Browser-decoupled auth after mint.
- Right-account verification built in.

### OPEN #1 — Credential-mint mechanism — RESOLVED (one follow-up pending) [from-code, verified on CLI v2.1.193]

Levi ran the isolated `setup-token` test (2026-06-25). Findings:

- **`claude setup-token` opened the DEFAULT browser** → confirms the cookie-grab trap live; the
  token was minted against whatever account the default browser held (admin@nascentech.com). Mint
  still requires a browser; incognito-URL ritual remains relevant.
- **It printed a standalone token to the terminal**: `sk-ant-oat01-…`, "valid for 1 year", with the
  contract `export CLAUDE_CODE_OAUTH_TOKEN=<token>`. (This token is now burned/to-be-revoked — it
  was pasted into chat.)
- **It did NOT write `.credentials.json`.** The slot dir got `.claude.json` (341 B config/state) +
  `backups/` only. No credential file.
- **`claude auth status` still reported `loggedIn: false`** in the slot after mint, and the
  dir-copy transplant (step 6) was also `false`.

**Interpretation (verified-fact portion):** `setup-token` does NOT create a CLI "login session." It
mints an **inherently portable bearer artifact — a 1-year OAuth token string — consumed via the
`CLAUDE_CODE_OAUTH_TOKEN` env var.** The credential is the string itself; it is not stored in the
config dir and is not what `auth status` checks (as tested). So the original "transplant a credential
into a slot" framing is replaced by "inject a token string via env var." Portability is trivial — a
string. Browser-decoupled after mint. Cross-platform credential divergence (keychain vs file)
**dissolves** — env var works identically everywhere.

**New design question this surfaces (feeds #2):** two env-scoped levers now exist —
`CLAUDE_CONFIG_DIR` (isolates *state*: settings, project state, session history, `.claude.json`) and
`CLAUDE_CODE_OAUTH_TOKEN` (carries *identity*). Emerging slot model: **slot = config dir + bound
token**, both set together from one label.

**Follow-up test — RESOLVED [from-code, verified CLI v2.1.193, 2026-06-25].** Clean one-line run
(`CLAUDE_CONFIG_DIR=<fresh> CLAUDE_CODE_OAUTH_TOKEN=<tok> claude auth status`) returned:
```json
{ "loggedIn": true, "authMethod": "oauth_token", "apiProvider": "firstParty" }
```
- Env token IS picked up from a fresh empty config dir → `CLAUDE_CODE_OAUTH_TOKEN` confirmed working.
- `authMethod: "oauth_token"` distinguishes env-token auth from stored login (`"claude.ai"`).
- **CONSEQUENCE for Verification UX (#4): NO `email` field is returned under `oauth_token`.** The
  stored-login form returns email/orgId/orgName/subscriptionType; the token form returns only
  loggedIn/authMethod/apiProvider. → The planned "match the email from `auth status`" verification
  does NOT work for env-token slots. Verification must shift to **mint-time identity capture**
  (human confirms which account in the browser; bind label→email in the registry) plus the
  `oauth_token`/`loggedIn:true` liveness signal. Live per-launch email match is unavailable via
  `auth status`. [Revisit in #4.]

### Why the email is missing — the caching mechanism [from-code, verified 2026-06-25]

Inspected `~/.claude.json` (lives at `$HOME/.claude.json`, and per-slot as `<CONFIG_DIR>/.claude.json`).
It contains a cached `oauthAccount` object: `emailAddress`, `accountUuid`, `organizationName`,
`seatTier`, `displayName`, **`profileFetchedAt`**, rate-limit tiers, etc.

→ `claude auth status` reports `email` by reading this **cached** `oauthAccount`, not by querying
the token live. `profileFetchedAt` proves the CLI fetches the profile from a network endpoint
(scope `user:profile`) and caches it. A fresh config dir + env token has no cached `oauthAccount`
yet → that's exactly why the `oauth_token` `auth status` showed no email.

**Scripted-verification hypothesis (Test E, pending):** running an actual token-authed `claude`
invocation in a slot should trigger a profile fetch that populates that slot's
`.claude.json` `oauthAccount.emailAddress` → readable by script. If true, right-account
verification is solved cleanly without reverse-engineering the endpoint or touching the keychain.

**Test E2 result — cache path CONFIRMED DEAD for token-auth [from-code, verified 2026-06-25].**
`claude -p "say ok"` with the token **succeeded** (`ok`, EXIT=0 — token works for real inference),
but the slot's `.claude.json` has **`oauthAccount: False`**. Keys present: cachedGrowthBookFeatures,
firstStartTime, machineID, **userID**, projects, etc. — no oauthAccount, no email. So under
token-auth the CLI never fetches/caches the profile. `auth status` and `.claude.json` will NEVER

**CLI surface check (Claude ran):** `claude auth` has only `login | logout | status` — **no
whoami/profile subcommand**. So scripted identity is not available out-of-the-box.

**→ Verification linchpin (the one LOCKED deliverable still unsolved).** Scripted right-account
verification for a token slot now has two candidate routes, both unverified:
  1. **Profile endpoint** — scope `user:profile` implies an identity endpoint; discover its URL via
     `claude -p "ok" --debug api` (a stored-login run fetches the profile → `profileFetchedAt`),

  2. **`userID` fingerprint** — the slot's `.claude.json` has a `userID`; if it's account-keyed

**Note:** the two minted tokens' true accounts are still unconfirmed (cookie trap) — a verification

### ⚠ ARCHITECTURE PIVOT — env-token works for HEADLESS/-p/SDK but NOT interactive [observed 2026-06-25]

Launching `CLAUDE_CONFIG_DIR=slot CLAUDE_CODE_OAUTH_TOKEN=<oat> claude` (INTERACTIVE, no `-p`) did
**not** use the token — it ran fresh-dir onboarding (theme select) then presented login options

the non-interactive path.) NOT yet 100% confirmed, but clearly observed once.

**Consequence — the architecture likely SPLITS by surface:**
- **SDK / headless concurrency** → env-token slots. PROVEN (the `-p` calls ran).
- **Interactive CLI-tab concurrency** → needs a **stored login per `CLAUDE_CONFIG_DIR`** (`auth login`
  once per slot), NOT the env token.
- → A slot may therefore = **config dir + (stored login for interactive) and/or (oat for SDK)**.

**New decisive open test (gates interactive concurrency on mac):** can macOS hold **two concurrent

### KEY DISCOVERY (Levi) — credential is hot-swappable on disk WITHOUT browser reauth [observed]
Levi hand-edited `~/.claude.json`, replaced the `oauthAccount` block with a previously-captured
**admin** block, and `/status` switched to admin — no browser reauth. This is the refined version of
his earlier keychain-transplant idea, and it points to a **no-reauth interactive switch**.

**CAVEAT (important): nameplate vs key.** He swapped only the `oauthAccount` *metadata*, not the
keychain `claudeAiOauth` credential (still truthtrek's tokens). So `/status` almost certainly showed

editing metadata). A **real** no-reauth switch must swap **both** the keychain `claudeAiOauth` blob
**and** the `oauthAccount` block. Captured-blob restore keeps the refreshToken alive → no reauth.
[Build-time spike: confirm full-swap really switches the operative account; confirm keychain write

### Credential storage shape — CORRECTED by Levi [from-code, verified 2026-06-25]

Keychain item `Claude Code-credentials` (acct `levi`, one per OS user). Its secret (`-g`) is a JSON
object **`claudeAiOauth`** with: `accessToken`, `refreshToken`, `expiresAt`, `scopes`
([user:file_upload, user:inference, user:mcp_servers, user:profile, user:sessions:claude_code]),
`subscriptionType`, `rateLimitTier`.

**CORRECTION (Claude overstated earlier):** the keychain `accessToken` is itself an
**`sk-ant-oat01-…`-format token** — same format as a `setup-token` oat. So oat and accessToken are
NOT different species, as previously claimed. They differ only in *value* (the two minted oats match
neither the stored accessToken nor refreshToken) and likely in *lifetime/refresh* (stored
accessToken pairs with a refreshToken + expiresAt; `setup-token` advertises a standalone 1-year
token). Lifetime/refresh distinction is plausible but NOT yet verified.

**Implication for the transplant idea:** more feasible than Claude first said — an oat could
plausibly be written into the `claudeAiOauth.accessToken` field. BUT the macOS concurrency
bottleneck stands regardless: the keychain item is a single shared name → stored-login swapping is
sequential/mutually-exclusive on mac. Feasibility ≠ concurrency. Env-token remains the concurrency
spine; transplant stays the sequential-only fallback.

### Architecture fork surfaced by Levi's keychain-transplant idea

Levi asked: save the generated tokens and script-write them into the keychain `accessToken` to switch?
- **As stated: off** — oat ≠ accessToken (he noticed they don't match); wrong type/lifetime, client
  expects to refresh it via refreshToken. Dropping an oat into accessToken would break.
- **General idea (swap the whole stored-login blob per account): real, but = the
  mutually-exclusive/sequential model.** The mac keychain item is a SINGLE shared name → swapping it
  is one-account-at-a-time and a running session's refresh can clobber/race. This is exactly the
  trap GROUND-TRUTH §7 named (public switchers). NOT our concurrency goal.
- **Env-token model sidesteps it entirely**: nothing in keychain, nothing shared, per-process.

→ **Leaning architecture:** env-token slots (concurrency spine) + scripted verification via
profile-cache (Test E). Keychain-transplant = rejected, documented as "why not." [HELD pending Test E.]

**Platform note:** on Linux/WSL the stored-login credential lives in `.credentials.json` INSIDE the
config dir → stored logins there are naturally per-slot/concurrent. The shared-keychain bottleneck
is macOS-specific. (Reinforces env-token as the portable spine.)

**Account facts corrected:** default account on this machine is **truthtrek@gmail.com** (GROUND-TRUTH
§1's `admin@nascentech.com` is stale). The minted token is also truthtrek@gmail.com (the account the
default Chrome profile held at mint — the cookie-grab trap, demonstrated).
