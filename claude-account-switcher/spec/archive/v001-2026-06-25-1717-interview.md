## Ingested LOCKED context (not re-litigated)

- **Objective.** Run multiple Claude accounts on one machine *truly concurrently*, with the right
  account guaranteed in each slot, where authorization is an explicit, portable artifact — not a
  side effect of which account the browser is logged into.
- **Concurrency includes the SDK.** Launching SDK agents under different accounts simultaneously.
  Mechanism must be env/process-scoped (works for interactive session and spawned SDK process alike).
- **Design spine:** slot/concurrency primitive = `CLAUDE_CONFIG_DIR` (per-process, empirically
  proven). Credential primitive = authorize once, capture portable token, plant into named slot;
  browser touched only at one-time mint. Public single-credential switchers are mutually exclusive,
  explicitly NOT our model.
- **Right-account verification is a deliverable** (`claude auth status` email match + guidance +
  error-checking).
- **Browser decoupling is a hard constraint.** After mint, nothing reads the browser session.
  Incognito preferred at mint.
- **Distribution:** private workshop in monorepo → export to a clean public repo
  `claude-account-switcher`. `deliverables/` is staging only.
- **Out of scope now:** team-provisioning / check-in auto-bind layer. Levi mints/holds accounts;
  teammates receive them. Future iteration.
- **Verified facts** in `GROUND-TRUTH.md` (CLI v2.1.191). Corrections carried: no `claude`
  incognito flag; isolation is per-process not per-keystroke.

### Constraints / non-negotiables to carry into ACs
- True concurrency (two processes, two accounts, no token hijack).
- Zero shell disruption (no PID-scanning wrapper, no forced sub-shell, no killing live sessions).
- Browser-decoupled auth after mint.
- Right-account verification built in.

string. Browser-decoupled after mint. Cross-platform credential divergence (keychain vs file)
**dissolves** — env var works identically everywhere.

**New design question this surfaces (feeds #2):** two env-scoped levers now exist —
`CLAUDE_CONFIG_DIR` (isolates *state*: settings, project state, session history, `.claude.json`) and
`CLAUDE_CODE_OAUTH_TOKEN` (carries *identity*). Emerging slot model: **slot = config dir + bound
token**, both set together from one label.

### Credential storage shape — CORRECTED by Levi [from-code, verified 2026-06-25]

Keychain item `Claude Code-credentials` (acct `levi`, one per OS user). Its secret (`-g`) is a JSON
object **`claudeAiOauth`** with: `accessToken`, `refreshToken`, `expiresAt`, `scopes`
([user:file_upload, user:inference, user:mcp_servers, user:profile, user:sessions:claude_code]),
`subscriptionType`, `rateLimitTier`.

**CORRECTION (Claude overstated earlier):** the keychain `accessToken` is itself an
**`sk-ant-oat01-…`-format token** — same format as a `setup-token` oat. So oat and accessToken are
NOT different species, as previously claimed. They differ only in *value* (the two minted oats match
neither the stored accessToken nor refreshToken) and likely in *lifetime/refresh* (stored
accessToken pairs with a refreshToken + expiresAt; `setup-token` advertises a standalone 1-year
token). Lifetime/refresh distinction is plausible but NOT yet verified.

**Implication for the transplant idea:** more feasible than Claude first said — an oat could
plausibly be written into the `claudeAiOauth.accessToken` field. BUT the macOS concurrency
bottleneck stands regardless: the keychain item is a single shared name → stored-login swapping is
sequential/mutually-exclusive on mac. Feasibility ≠ concurrency. Env-token remains the concurrency
spine; transplant stays the sequential-only fallback.

### Architecture fork surfaced by Levi's keychain-transplant idea

Levi asked: save the generated tokens and script-write them into the keychain `accessToken` to switch?
- **As stated: off** — oat ≠ accessToken (he noticed they don't match); wrong type/lifetime, client
  expects to refresh it via refreshToken. Dropping an oat into accessToken would break.
- **General idea (swap the whole stored-login blob per account): real, but = the
  mutually-exclusive/sequential model.** The mac keychain item is a SINGLE shared name → swapping it
  is one-account-at-a-time and a running session's refresh can clobber/race. This is exactly the
  trap GROUND-TRUTH §7 named (public switchers). NOT our concurrency goal.
- **Env-token model sidesteps it entirely**: nothing in keychain, nothing shared, per-process.

→ **Leaning architecture:** env-token slots (concurrency spine) + scripted verification via
profile-cache (Test E). Keychain-transplant = rejected, documented as "why not." [HELD pending Test E.]

**Platform note:** on Linux/WSL the stored-login credential lives in `.credentials.json` INSIDE the
config dir → stored logins there are naturally per-slot/concurrent. The shared-keychain bottleneck
is macOS-specific. (Reinforces env-token as the portable spine.)

**Account facts corrected:** default account on this machine is **truthtrek@gmail.com** (GROUND-TRUTH
§1's `admin@nascentech.com` is stale). The minted token is also truthtrek@gmail.com (the account the

### #4 verification linchpin — RESOLVED (definitively, by token scope)

The setup-token oat is granted **`user:inference` ONLY** — NOT `user:profile`. This is the structural
reason every scripted-identity route died (Route 1 endpoint, `.claude.json` cache, Route 2 userID):
the token **cannot** fetch the account profile/email by design. Scripted live email-readback is
therefore **permanently impossible**, not merely undiscovered.

→ **label→email is established once, at mint, by human attestation** — and the mint flow makes that
attestation reliable rather than blind:
  - consent page **shows** the authorizing email (read, don't guess);
  - **Switch account** corrects a cookie-trap mismatch in place;
  - incognito/logged-out route **forces** the human to be the account chooser.

The oat can never change accounts after mint, so a once-correct binding stays correct. Only residual
failure mode = fat-fingering the email into the registry at capture (mitigation = capture-step
confirm; tool cannot auto-read the email since it lives browser-side and the oat lacks profile scope).

## Capture/store shaping — onboarding vs activation, seams [from-user, 2026-06-26]

**Boundary refinement (Levi).** Team-provisioning layer is NOT built this iteration, but v1 must
make it *feasible* — design the seams. Two distinct flows to prepare for:
- **Onboarding (first-time):** mint oat → capture+confirm email → (optional) associate mint context
  → store the slot. Sets a slot up.
- **Activation / "check-in" (recurring):** select an existing slot → bind the environment
  (`CLAUDE_CONFIG_DIR` + `CLAUDE_CODE_OAUTH_TOKEN` for SDK; reauth-or-config-dir-slot for
  interactive). Does NOT re-mint. The team "check-in" wrapper is the deferred layer; its core is
  this v1 `use`/activate command.
→ Command surface gets `add`/onboard (mint+store) vs `use`/activate (select+bind) as separate verbs.

**Secret capture = auto-scrape (DEC-005).** Tool drives `setup-token`, captures the oat from stdout
(no human copy/paste of the secret); email is retype-confirmed. A manual-entry path (paste oat +
type email) is a possible secondary option — parked, revisit at command-surface pass.

**Mint browser context (capture step).** Recommended path = a dedicated logged-out Chrome profile
(persistent, re-launchable for rotation, robust vs incognito's already-running flakiness); fallbacks
= incognito, manual paste. Tool surfaces URL + directions for both, attempts auto-open, degrades
gracefully. The richer enumerate-profiles→associate→verify flow is deferred (D-002), with a cheap v1
seam (optional per-label mint-context profile id).

**Store schema = record-per-label (option 3, minimal).** Each label keys a RECORD (object:
`{email, oat, …}`), not a bare oat string. This is the cheap seam that lets the interactive
credential (D-001) and profile-anchor (D-002) layers slot in later WITHOUT building them now.
DEC-004 unchanged (no decision superseded). Levi's "don't build unused machinery" honored: schema
hygiene, zero swap/capture logic written this iteration.

**`rm`/revoke command.** Drops the oat from the store AND walks the human through server-side
revocation in settings (no CLI revoke subcommand exists; revocation is web-UI only). Safe-ID rule as
above. "Enforce burning on rotation" = lifecycle polish, v1-lite (warn on stale) or deferred.
