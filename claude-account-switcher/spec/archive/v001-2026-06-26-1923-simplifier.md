# Simplifier Critique — v001 spec (2026-06-26)

## Pass 1 — Catalog

Components cataloged: 7 AC groups (AC1–AC7), 28 leaf ACs, 5 phases, 3 deferred items with named seams (AC1.4, AC1.2 schema), 1 dual-name distribution decision (AC7.3).

## Pass 2 — Challenge

**AC2.2 — three-path browser routing.**
Path (1) ("dedicated logged-out Chrome profile if one is configured") is dead in v1. Chrome-profile enumeration is D-002; the `mint_profile` field is stored but unused. Path (1) will never trigger unless the user manually configures something the tool doesn't yet support. Cut path (1) from AC2.2; keep paths (2) and (3). This removes a code branch with no v1 exerciser.

**AC2.3 — explicit user direction to read the consent page.**
This AC is a printed message, not a behavior. It exists solely to set up the email retype-confirm in AC2.6. Collapse AC2.3 into AC2.6's prompt text ("Before typing: confirm the consent page shows the intended account"). One fewer AC, zero lost behavior.

**AC3.6 — dead-token exit-signal capture.**
Capturing a child's exit signal to detect auth errors and print re-mint guidance is meaningful complexity for a power-user CLI. The error will appear in the child's stderr anyway; the user is capable of reading it and running `cas rm`. This AC earns its keep only if the signal is reliably distinguishable and the guidance is materially different from what the child already prints. If not confirmed, cut or defer.

**AC6.3 — interactive "offer to delete slot config dir" on rm.**
Adding a confirmation prompt inside `rm` is ceremony. If a label is removed from the store, the slot dir is orphaned and serves no purpose. Delete it unconditionally; document the behavior. Cut the interactive branch.

**AC7.3 — dual CLI names.**
`claude-switch` is declared canonical but `cas` is used everywhere in the spec. Two installed names adds install and documentation surface with no functional benefit for a solo tool. Pick one; defer aliasing until there's an audience that needs it.

## Pass 3 — Minimum viable cut list

If shipping faster were the goal, cut: AC2.3 (collapse into AC2.6), AC3.6 (defer), AC6.3 interactive branch (always delete), AC7.3 second name (ship `cas` only). No core deliverable is affected.

## Pass 4 — Over-specification

**Phase 4 "Depends on Phase 3" is a sequencing preference, not a technical dependency.** `list`, `use`, and `rm` have zero code dependency on `run`. The stated rationale ("exercisable end-to-end before management verbs") means developer workflow, not architecture. Consequence: `list` cannot ship until the runner is complete, even though it depends only on Phase 1–2. Consider splitting Phase 4: move `list` into Phase 2 (records exist the moment `add` works; you need to see them) and keep `use`/`rm` as Phase 4. The 5-phase count stays but the dependency chain becomes honest.

**AC5.1 bakes in a flag that may not exist.** "`claude auth login --email <stored-email>`" is a mechanism, not a requirement. If the flag doesn't exist, this AC is wrong. State the requirement: "initiates reauth for the stored label's account without the user needing to look up the email." Implementation discovers the mechanism.
