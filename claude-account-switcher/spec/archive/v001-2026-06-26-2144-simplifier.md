# Simplifier — Revision 2 Critique
> Spec: claude-account-switcher · Revision 2 · 2026-06-26

## Pass 1. Catalog

AC2.2 now contains six distinct behaviors: (1) enumerate Chrome profiles with name+Google email, (2) prompt user to select one, (3) bring that profile's window to the front, (4) open the OAuth URL in the selected profile, (5) fallback: open URL in default browser AND print it for manual paste, (6) announce the chosen path. AC1.4 and the Out-of-scope D-002 entry exist to accommodate AC2.2's `mint_profile` artifact.

## Pass 2. Challenge

**Window-focus is over-specified mechanism, not requirement.**
"Brings that profile's window to the front" prescribes an OS-level action (AppleScript / `open -a` tricks). The requirement is "user completes auth in the correct Chrome profile." Whether the window gets focus is an implementation detail — and on most systems, opening a URL in a named Chrome profile will focus it automatically. Cut window-focus from the spec; implementation can do it if trivial, but spec shouldn't mandate it.

**The fallback is doing double duty.**
"Opens the URL in the default browser AND also prints it for manual paste." These serve different intents: one assumes the default browser is acceptable; the other assumes the user wants incognito. Specifying both is hedging. Pick the more universal: print the URL only. If the user wants to open it in a browser, they will. The "open in default browser" adds an unrequested side effect that may open a logged-in session the user doesn't want.

**The enumeration format is over-specified.**
"Name + Google email, read from Chrome's local state" prescribes the data source and display format. The requirement is "user can distinguish which profile to select." The implementation path (Chrome's local state JSON) is a detail.

**AC2.2 is not a leaf — it's a sub-tree.**
A leaf is independently testable. AC2.2 contains at least four independently testable behaviors (enumerate, select, open, announce + fallback branch). This won't cause a spec failure, but the Phase 2 implementation will be harder to scope without internal sub-tasks.

## Pass 3. Minimum viable cut list

1. Remove "brings that profile's window to the front" from AC2.2.
2. In the fallback, drop "opens the URL in the default browser and" — keep only the print.
3. Remove "read from Chrome's local state" — format and source are implementation.

None of these remove capability. They remove mechanism-prescription from the spec layer.

## Pass 4. Over-specification flag

AC2.2 specifies the data source (`Chrome's local state`) and display format (`name + Google email`) for profile enumeration. Both are implementation decisions. The spec requirement is: "user can identify and select a Chrome profile." How the tool reads or formats that list is not a spec concern.
