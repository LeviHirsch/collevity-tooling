# Contrarian Review — Revision 2
> Spec: claude-account-switcher v001, Revision 2
> Reviewer: Contrarian persona
> Date: 2026-06-26
> Focus: AC2.2 Chrome-profile mint-routing reframe; profile email vs Claude email confusion

---

## Pass 1 — Assumptions made explicit

**AC2.2** assumes:
1. The chosen Chrome profile has at least one open window to bring to the front.
2. "Bring window to front, then open URL" reliably causes Chrome to open that URL inside the already-focused profile's window, not in whatever profile Chrome internally decides to use.
3. Chrome's `Local State` JSON file (profile enumeration source) lives at a stable, known path and carries a stable schema across Chrome releases, Chrome variants (Beta, Canary, Chromium), and future macOS versions.
4. The Google email shown per profile in the selection UI meaningfully helps the user identify which profile to pick for a given Claude account.

---

## Pass 2 — Inversions

**Assumption 1 inverted.** If the chosen profile has no open window, there is nothing to bring to the front. The spec does not describe what happens: does the tool open a new Chrome window in that profile first, fall back silently, or error? The fallback path is defined for "Chrome unavailable" but not for "profile exists but has no window." This is a gap.

**Assumption 2 inverted.** Chrome's URL-routing when already running is the exact problem AC2.2 was designed to solve (because `open --args` is unreliable). The proposed fix — focus a window, then open — does not guarantee Chrome routes the subsequent `open` call to the focused profile. Chrome may open the URL in the most-recently-used profile regardless of which window has OS focus. The spec treats "focus-then-open" as a solved routing mechanism, but it is an assumption, not a verified technique (contrast with DEC-010, which verified stdout behavior via a spike).

**Assumption 3 inverted.** `Local State` is an undocumented internal. Chrome Beta and Canary use different paths; Chromium omits the Google email field entirely in some builds. No spike is noted verifying the path, schema, or field name.

**Assumption 4 inverted.** The D-002 caveat states explicitly: Chrome profile Google email ≠ Claude account email unless the user logs into Claude via Google SSO. AC2.2 surfaces the Google email as the label in the selection UI. A user running Claude under a non-Google email (or a *different* Google account) will see a list of Google emails that are meaningless for identifying which profile holds the right Claude cookie. The spec does not warn the user of this distinction at the selection step.

---

## Pass 3 — Challenge the problem statement

AC2.2 exists because `open --args` is unreliable when Chrome is running. The replacement mechanism (focus window → open URL) is also an untested workaround against the same underlying Chrome behavior: Chrome decides where URLs go, not the caller. The spec may be adding complexity to solve a problem that the portable fallback (print URL, user pastes into the right profile manually) already handles correctly — with full user agency over where the URL lands.

---

## Pass 4 — Biggest risk

The focus-then-open sequence is assumed to route the OAuth URL into the chosen Chrome profile, but this is not verified and may not hold. If it silently fails, the URL opens in the wrong profile, the user authorizes the wrong Claude account, and the fat-finger risk AC2.6 was designed to catch goes undetected — the user types the email they *intended*, not the one the consent page actually showed.
