# Contrarian critique — v001 spec (greenfield iteration 1)
Date: 2026-06-26

---

## Pass 1: Explicit assumptions

1. **`setup-token` prints the OAuth URL to stdout** (AC2.1, AC2.4). The spec declares "Open questions: None" yet explicitly flags "confirming the OAuth URL appears on stdout vs. only the browser address bar" as a pending spike — demoted to "implementation-level." That is the wrong classification. If the URL goes only to the browser, AC2.1–AC2.4 collapse: no capture, no auto-scrape, no liveness check input. The entire Phase 2 auto-flow is contingent on this unconfirmed behavior.

2. **`claude auth login --email <stored-email>` is a real CLI flag** (AC5.1). No empirical confirmation appears in decisions.log. DEC-004 records the decision to use `auth login` but never tests `--email` as a valid option. If the flag doesn't exist, `use` fails completely at first run.

3. **`list` can identify the active interactive login via email match** (AC4.2). DEC-001 confirmed the oat-token auth path returns NO email. The spec does not confirm whether the default-config interactive path returns a stable, parseable `email` field. If it doesn't, AC4.2's match is broken.

4. **Dead-token authentication errors are detectable at the subprocess boundary** (AC3.6). "Captures the exit signal" is ambiguous. Auth errors, network errors, and user-code failures may all exit non-zero with no distinguishable signal. The AC specifies behavior without verifying it is implementable.

5. **Retype-confirm prevents mis-bind** (AC2.6). A user who mistypes an email consistently — typing the same wrong address twice — defeats the entire binding verification mechanism. The binding is write-once with no recovery path short of `rm` + re-add.

---

## Pass 2: Inversions

- "Incognito context is reliably logged out" (AC2.2) → Passkeys and device-bound sessions can bypass incognito session isolation. The "logged-out context" guarantee is auth-method- and browser-version-dependent.

- "Phase 4 depends on Phase 3" (phases section) → `list`, `use`, and `rm` need only Phase 1 + Phase 2 to be technically testable. Locking them behind Phase 3 prevents using them to validate the store before tackling concurrency. The earliest `rm`-then-re-add debug cycle is deferred unnecessarily.

---

## Pass 3: Problem challenge

AC2.1–AC2.4 assume `setup-token`'s output format is stable across CLI versions. If Anthropic changes the flow (stdout token → browser-only, or restructures the printed output), the mint ritual breaks silently. No spec-level mitigation exists.

---

## Pass 4: Biggest risk

The unconfirmed stdout assumption in AC2.1. If `claude setup-token` routes the OAuth URL directly to the browser without printing it to stdout, the auto-capture pipeline (AC2.1 → AC2.4) is speculation, and every subsequent phase builds on a broken foundation. This should be an explicit verified spike, not a closed question.
