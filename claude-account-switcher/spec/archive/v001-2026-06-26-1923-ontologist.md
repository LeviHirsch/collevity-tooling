# Ontologist Critique — claude-account-switcher spec v001
> Date: 2026-06-26 | Reviewer: ontologist persona | Mode: greenfield

---

## 1. Essence

Strip the CLI surface away: this is a **named credential vault with isolated subprocess injection**. The goal statement captures this accurately — "explicit, portable, per-process artifact" maps cleanly to the essence. The "right account guaranteed" phrasing is consequence-level, not mechanism-level, but it doesn't mislead. No issue here.

## 2. Root cause

The spec is addressing a genuine root problem: Claude conflates auth identity with global shell/browser state, making per-process identity impossible. This is not a symptom of a deeper need — it is the need. The stated goal would generalize ("any tool that ties credentials to ambient global state"), but the spec isn't trying to generalize, and that's appropriate.

One sharp edge: the Goal says "right account guaranteed in each slot." The Success Criteria anchor this guarantee to write-once email binding at mint (AC2.6). That is not a guarantee — it is a human-discipline assumption. AC2.6 prevents auto-error; it cannot prevent the user typing the wrong email. The claim "no false-positive is possible because the binding is write-once at mint" (AC3.3) is false by inspection: a false-positive is entirely possible if the user misreads the consent page. The spec should say "no automated false-positive" and acknowledge the human-attestation assumption explicitly.

## 3. Prerequisites

Two load-bearing assumptions are dismissed as "implementation-level" in Open Questions, but they are spec-level risks:

- **AC2.1 / AC2.4** assume `claude setup-token` emits the OAuth URL to stdout in a parseable form. If the URL goes only to the browser address bar, the entire `add` auto-scrape mechanism (the primary UX differentiator from manual flows) breaks. This is the most consequential unverified dependency in the spec.
- **AC4.2** assumes `claude auth status` returns a machine-parseable payload with an `email` field. **AC5.1** assumes `claude auth login --email <addr>` is a valid CLI flag. Neither CLI signature is confirmed. These are small but non-trivial.

## 4. Hidden assumptions

- The store schema (`AC1.2`) uses email as a human-supplied label field, not a system-verified one. No deduplication by email across labels is enforced — two labels can silently store the same account under different names with no warning. Probably acceptable for v1, but not stated.
- `chmod 600` is asserted as sufficient (FileVault backs it); this is an explicit deferral, not hidden. No issue.

## 5. Phase ordering

Phase 4's "Depends on: Phase 3" is the item under scrutiny. The body text is honest — "Phase 3 must be in place so the tool is exercisable end-to-end before management verbs are layered on" — this reads as demonstrability ordering, not data dependency. But the formal `Depends on:` field lists Phase 3 alongside Phase 1 and Phase 2 without distinguishing kind. Phase 1 and Phase 2 are data dependencies (Phase 4 needs the store and valid records). Phase 3 is only a workflow preference. Grouping them as peers in a `Depends on:` clause misrepresents Phase 3's nature. Suggest: distinguish with a `(sequencing, not data)` qualifier inline, or use a separate `Ordering note:` line.
