- **What this is:** the field-level JSONL schema for the Collevity entry store — the keystone every pipeline part reads/writes. Replaces today's 3-column Excel Dropper (`Thing`/`Timestamp`/`modified`, 852 rows, flat untyped pool). `[from-user]`
- **First landmark (v1 emphasis):** capture **raw USER entries.** v1 `author` ≈ always user; agent-authored entries are deferred/additive. `source` still varies (dropper/mobile/claude-hook). `[from-user]`
- **Model:** every record is an **`entry`** (universal unit) + **orthogonal facets**, not one overloaded `kind`. `[from-user]`
- **Type → `tags` (multi-valued):** one entry can carry several types of info ("sleep+meds+exercise+devos" in one drop). Growable; usage reveals promotion. `[from-user]`
- **thing/event demoted** from master discriminator to one facet (`entity_axis`) used mainly for projection — possibly just a property. `[from-user, open]`
- **Three orthogonal origin fields, kept distinct:** `source` (channel) · `author`/provenance (who) · `context_ref` (originating session/location/thread). `[from-user]`
- **Now-horizon:** `horizon: actual|projected` (a drop is a log OR a plan) + distinct times: `created_at`, `occurred_at?`, `planned_for?`, all UTC + `tz` offset (fixes the MDT/EDT bug at root). `[from-user]`
- **Storage:** JSONL, one append-only pool; per-context = views, not partitions. Append-revision (not in-place) for versioning; the live `modified` column already hints this. `[from-user]`
- **Hard constraint:** must keep feeding `read_dropper_day.py` / `/checkin` — emit {text, created-ts} per day. Migration of the 852 rows is additive; nothing breaks. `[from-code]`
- **Friction guarantee:** capture writes only cheap top-line fields; ingest/AI fills structure. This division line *is* the friction guarantee. `[from-user]`

## Socratic interview

### Q1 — capture-time required minimum (the division line)
**Q:** At capture, before AI touches it, what's the minimum an entry must carry? A (bare floor: text/created_at/tz/source/author) · B (floor + optional horizon/tag taps) · C (required horizon)?
**A (Levi):** Not C. Likes **B to test**, but wants the option to **revoke later** if needed. `[from-user]`
**Resolution:**
- Required floor = A's fields: `text`, `created_at`, `tz`, `source`, `author(=user in v1)`. Everything else optional/derived.
- **B layered on top as the capture experience** — optional `horizon`/`tags` taps. **Crucially: B vs A is a capture-SURFACE config, not a schema fact.** The schema always treats `horizon`/`tags` as optional+derivable, so "revoking B" = stop offering the tap; no schema change, no migration. Reversibility guaranteed by construction. `[from-user]`
- C rejected (required horizon = too much capture friction; violates friction guarantee).

### Q2 — modeling source-specific context (session reconstruction)
**Q:** How to model context that matters for some channels (claude-session → must rebuild a session's prompts in order) but is unused by others (mobile/dropper)? (1) flat optional fields · (2) `source` + optional source-shaped `context` object · (3) generic `context_refs[]` list.
**A (Levi):** Raised the need; essential to rebuild a session's prompts; field may be unused by other channels; asked for recommendation. `[from-user]`
**Resolution (proposed, pending confirm):**
- Keep **`source`** = always-present simple channel tag (`mobile`/`dropper`/`claude-hook`).
- Add **optional `context`** object, shape keyed to source — `(2)`. For `claude-hook`: `{ kind: "claude-session", session_id, seq, parent_id? }`. Absent for channels with no context (free in JSONL).
- `session_id` groups; `seq` orders explicitly (not just `created_at`); `parent_id` optional (forked/continued sessions; SPP lineage).
- Designed for easy growth to `(3)` (object → list) if entries later need multiple context refs (likely).
- **Populated by the prompt-capture-hook (part 3); schema only RESERVES the shape now.** Claude-prompt drops are user entries (author=user) → in v1 scope.
**Resolved (Levi):** **(2)** — `source` + optional source-shaped `context` object; designed to grow into the (3) list form later. `[from-user]`

### Q3 — how much is a "thing"? (entity modeling + the `entity_axis` field)
**Q:** You said *"everything is an entry"* and we demoted thing/event to a facet. But there's a real fork in *how much* a "thing" is:
- **(a) Uniform pool** — a "thing" is just an entry that *represents* a durable entity (a project/person/protocol), distinguished by tag/type and pointed at by other entries' `links`. One object type. "Everything is an entry" stays literally true. No required `entity_axis` field — thing-ness is a tag or a derived marker; the ledger materializes "things" as a view.
- **(b) Two object types** — `entry` (the event/drop stream) and `thing` (durable entities as first-class nodes with their own identity) that entries attach to. A graph of entries + things. Closer to the THING-parent ontology / knowledge-graph.
- **(c) Hybrid** — uniform pool now (a), but reserve a `promotes_to_thing` / entity id so ingest can later "promote" an entry into a first-class thing without migration.
**A (Levi):** The entity/"things" layer is **outside the scope of this part.** This part = **one database = the core of the horizontal stream**: a *time-anchored implementation stream*. v1 = these (user) entries. Later: (i) more kinds of events/entries on the timeline (e.g. system events) — still horizontal, same DB; (ii) a separate, *derived* **vertical** DB for entities/things — "a data strata to complement the data lake." `[from-user]`
**Resolution (SCOPE BOUNDARY — key):**
- This part builds the **horizontal append-only time-stream = the data lake.** Entity/thing/graph modeling is a **future, separate vertical store** (derived mart/strata) — OUT of scope here. **Amends §2:** drop the `entity_axis` facet.
- "Everything is an entry" = everything *in this store* is a stream item; entities live in a different DB.
- **Stream-item-kind discriminator DEFERRED (Levi):** do **not** add a `kind`/`entity_axis` field in v1. He doesn't want to pre-decide the mechanism (multiple valid ways). `source` + `tags` already give a handle to distinguish future system events; decide the explicit mechanism when they arrive. `[from-user]`

### Q4 — edit / revision behavior on an append-only stream
**Q:** Append-only stream, but you have a `modified` column today and have flagged wanting to edit entries after the fact (and "plans versioned into histories"). How should an edit behave? (a) in-place mutate (change text, bump `modified`) · (b) append-revision (new version, shared `lineage_id`, latest-wins; history retained) · (c) defer edit semantics to the app-wrapper (slot 6); v1 = capture only, just keep `created_at`/`modified` stamps.
**A (Levi):** Unsure — sees value in traceable edits (b), but also edits entries to correct his own errors, and thinks allowing edits matters for moving toward cleaned content/context. Leans a or b; asked for recommendation. `[from-user]`
**Resolution (REVISED per Levi pushback — see DEC-006):** Levi: revision *history* is an entity concern → out of scope; edits here are only *corrections* to user entries (like the Excel), not versions of things; doesn't want lineage complexity. So: **edits = in-place correction (rewrite entry, bump `modified`); NO `lineage_id`/`supersedes`/revision history. "Append-only" relaxed → append-on-drop, edit-in-place-on-correction.** (My earlier append-revision proposal withdrawn — over-spec.) Tradeoff: in-place edits = small sync-conflict surface; day-partition later if it bites. `[from-user]`

### Q7 — should `tags`/type also be out of scope?
**Q (Levi):** Once the stream triggers creation of entity items (tasks/records), the type lives on those entities — skipping the need for a type field. But tags could be useful *now* as a crude filtering/associating field for ad hoc exploration. Thoughts? `[from-user]`

### Q8 — remaining mechanical fields (recommended defaults for confirm)
*(Conceptual forks done; these are near-default mechanical calls presented as a batch under the thin-stream principle.)*
1. **`id`:** UUID v4, generated at capture by the writing surface (no cross-surface coordination). Excel→JSONL ingest uses a **deterministic id = hash(text + created_at)** so re-running the ingest is idempotent (no dupes). Other surfaces: random uuid.
2. **checkin-compat:** a thin `read_day(date)` over the JSONL (filter by `created_at` date → {text, time}), wrapping/replacing `read_dropper_day.py`. Excel rows flow in via ingest so the day-read sees them.

4. **horizon/times:** `created_at` required; `occurred_at`/`planned_for` optional/derived; `horizon` (actual|projected) optional — **derivable from which time is set**, stored explicitly only when user taps it (B). No required horizon flag.
**A (Levi):** No objections raised; asked clarifying follow-ups on #2 (checkin-compat) and the Excel ingest. Clarifications given:
- **#2 mechanism:** swap `read_dropper_day.py` internals xlsm→JSONL, keep CLI + output identical → `/checkin` unchanged. `read_day(date)` filters by local-day of offset-aware `created_at` (fixes the tz mis-bucketing bug). - **Ingest cadence:** **on-demand at read-time** (piggybacks on whoever reads — checkin, table-view); idempotent + sub-second so safe to run every read; no daemon/cron. Incremental (watermark) only if it ever grows; scheduling only if a non-interactive consumer needs fresh data.

### Q1-redux — id minting, dedupe, Excel bridge, and the flex-field family
**Q:** Lock the id/dedupe/Excel mechanics from Q8?
**Discussion (Levi pushed on several of my Q8 defaults):**

- **id minting — moved off the surface (Levi questioned "why surface-minted?").** My Q8 default (each surface mints a UUID) was a distributed-systems reflex for offline-first clients that need identity *before* reaching the store. Levi doesn't have that in v1. Agreed model: **canonical id minted on append by the store seam (`append_entry`)**, single place. Levi's own framing: surfaces *may* track their own local ids transiently, then those are demoted and the core assigns the canonical id on append — this is the recognized client-local-id / server-authoritative-id pattern and preserves a clean upgrade path to true offline-first later. v1 only commits "canonical id assigned on append." `[from-user]`
- **id format = UUIDv7.** Taught the UUID version landscape (v1 time+MAC/leaky, v3/v5 deterministic hash, v4 random, v6/v7 time-ordered, ULID cousin). Chose **UUIDv7**: time-ordered (free chronological sort + index locality on the future Postgres rung), standardized (RFC 9562), drops natively into Postgres `uuid` column (ULID would not — it's not a UUID). 128-bit size is irrelevant at this scale. Python: stdlib in 3.14, tiny lib before. `[from-user]`
- **dedupe — off the schema.** Not a real concern at this scale. The only need is "Excel bridge shouldn't re-add a row each run" = *bridge idempotency*, not DB dedup. `[from-user]`
- **Excel must NOT dictate the core (Levi's principle).** Since Excel is being phased out, the core JSONL is designed **Excel-blind**; everything Excel-specific lives in the **bridge script + a sidecar state file** (`excel-ingest-state.json`) mapping Excel-row (drop-timestamp) → JSONL id + a snapshot of last-ingested text. Retire Excel = delete bridge + sidecar; core untouched. `[from-user]`
- **edit-after-read — solved by snapshot reconciliation, in the bridge.** Rejected Levi's two offered commitments (edit-immediately-or-lose-it; manual reingest flag) in favor of a third: the sidecar's per-row text snapshot lets each ingest diff rows — new→append, changed→rewrite mapped entry, unchanged→skip. Auto, idempotent, edit-propagating, zero manual effort, entirely bridge-side. **Levi's assessment confirmed correct: this works *only because* the dataset is small (O(n) full re-diff per read is cheap) AND Excel is temporary (we skip deletion/conflict handling). If either changed, the approach would change.** Deletion of Excel rows is an unhandled gap; deferred. `[from-user]`
- **`modified` column dropped from v1.** Buggy in Excel (updates on click). The bridge reads **only `{text, drop-timestamp (col E)}` and explicitly ignores `modified`** — so it can't pollute the JSONL; Levi need not touch Excel. This ignore-rule must be **recorded as protocol** in the spec + an acceptance criterion. A `updated_at` is trivially re-addable later if a need appears; none now. `[from-user]`
- **flex fields — a deliberate "schema doesn't have to commit early" tier, two flavors:**
  - **`meta_notes` (string, prose)** — unstructured human/AI annotations *about* the entry (edit jottings, breadcrumbs). Safe *because* it's prose (can't silently become a queryable schema). **Light convention only:** append-only, one line each, `ISO-timestamp — free prose`, newest at bottom. No typed prefixes / categories (Levi's `(init):`/`(timestamp):` idea declined as redundant + too semantic). **Tripwire:** wanting typed prefixes = signal to promote to structured stash or a real field.
  - **`source_data` (object) — the structured stash / schema-on-read.** Levi's articulation (confirmed exactly right): preserve *structured remainder from the source* verbatim when it doesn't warrant core fields — neither discard (lossy) nor promote-everything (rigid). Pure lake instinct (DEC-005/009): store raw, structure accretes on read; promote a stashed field later with history intact. **Optional**, reserved in v1, not required to populate; first natural populator = claude-hook session payload (part 3); Excel produces nothing to stash. Name chosen `source_data` (over `raw`/`extra`).
  - **Auxiliary-field family (kept distinct):** `tags` = ad-hoc labels (DEC-008) · `meta_notes` = prose about the entry · `context` = *designed* source-shaped context (DEC-002) · `source_data` = *undesigned* raw source remainder. `context` is structure we designed; `source_data` is structure we refuse to lose. Excel↔JSON row correlation lives in the **sidecar**, NOT in any entry field.
**Resolution:** All of the above locked by Levi ("I give my nod"). → **DEC-010** (id), **DEC-011** (Excel bridge + modified-ignore), **DEC-012** (flex-field family). `[from-user]`

## Conclusion

**Goal.** The field-level JSONL schema for the Collevity entry store — a thin, append-only, horizontal time-stream of (v1: user) entries that replaces the flat 3-column Excel Dropper and keeps feeding `/checkin`. The keystone every pipeline part reads/writes.

**Guiding principle (Levi).** *This data lake logs precise events as they actually happened.* Horizon/planning, typing, entities, and revision history are **strata-layer** concerns downstream — the horizontal stream stays deliberately thin (DEC-009).

**Constraints.** Preserve `/checkin` (output parity via a `read_day` seam); JSONL physical store for v1 but logically portable up the ladder to SQLite → Postgres/Supabase (DEC-005); capture-friction guarantee (cheap required floor; AI/ingest fills structure); Excel remains a live capture channel through the transition, designed Excel-blind in the core (DEC-011); single-user / local / private.

**Success criteria.** (a) a drop from each live channel lands as a valid record carrying the required floor; (b) `/checkin` reading JSONL matches Excel-era output for the same day; (c) the 852 Excel rows ingest idempotently (re-run → no dupes; text edits propagate as updates); (d) local-day bucketing — evening/late-night drops appear on the day they were made, not the next UTC day.

**Scope boundary (out).** The entity/"things" vertical store; revision/lineage history; `tier`/retention; the `kind`/`entity_axis` discriminator; the capture surfaces themselves (mobile / hook / computer-dropper UI are separate parts); query/embeddings/SQLite engine work; `occurred_at`/`planned_for`/`horizon` fields (strata-era promotions).

**Root-vs-symptom.** Root: the pipeline has no real entry model — a flat, untyped, single-channel, tz-broken spreadsheet can't carry the provenance, time-correctness, and multi-channel capture everything downstream depends on. "Excel is clunky" would be the symptom.

**Final v1 field set.** Required: `id` (UUIDv7, store-minted) · `text` · `created_at` (ISO-8601+offset) · `source` · `author`. Optional: `context` · `tags` · `meta_notes` · `source_data`. (Decisions DEC-001..014.)
