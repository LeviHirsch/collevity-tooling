## Pass 2. Component challenges

**AC3.1 — over-long prose leaf.** This AC does five things in one sentence block: defines pure-retrieval behavior, establishes consumer composition pattern, clarifies parity scope, corrects tz mis-bucketing, and scopes future read shapes. That is a policy memo, not a testable criterion. The tz correction belongs in AC3.2. The consumer composition pattern (call `sync_sources` first) belongs in AC5.1 — where it already partially appears. The future-read-shapes note is Out of Scope material. Strip AC3.1 to: "`read_day(date)` reads the JSONL pool and returns `{text, time}` per entry for that day; it performs no writes or ingestion." One sentence, independently testable.

**AC5 as a group — thin justification for a permanent seam.** AC5.1 and AC5.2 together say: there is a `sync_sources` boundary, it has one registered ingester (Excel bridge), and the multi-source registry is deferred. The problem: if multi-source registry is deferred and there is only one ingester, `sync_sources` in Phase 1 is a boundary with no body — an empty dispatch loop. The spec calls `sync_sources` "permanent" but its v1 implementation is a stub that calls one function. That is fine operationally, but the spec over-describes the future shape (pluggable registry, per-source freshness machinery) for something that does not yet exist. AC5.2's "shaped so a second pull source plugs in additively" is forward-justification, not a v1 requirement. Cut the forward language; keep only what Phase 1 must deliver: a callable `sync_sources()` that runs the Excel bridge. Future extensibility is an implementation concern.

**Constraints section — Offset correctness paragraph** (the long bullet starting "Offset correctness is owned at capture, not here"). This paragraph explains the Excel tz exception, references the legacy 852 backfill, and names EDT. That content belongs in AC4.4, where it already lives in full. The constraint bullet duplicates it. Cut the bullet to one sentence: "Each capture surface owns its own offset stamping; this part assumes correctness."

## Pass 3. Minimum viable cut list

If forced to ship Phase 1 in half the time:

- **AC5.2** forward-justification language — cut "The general multi-source registry / per-source freshness machinery is deferred; the `sync_sources` contract is shaped so…" down to "v1 implements exactly one ingester: the Excel bridge (AC4)."
- The consumer composition pattern duplicated across AC3.1 and AC5.1 — consolidate in AC5.1 only.

---

## Pass 4. Over-specification flags

- **AC3.1** prescribes the consumer call-order contract (`sync_sources()` then `read_day()`) inside a read-seam AC. Call-order is an op-path concern, not a schema or seam requirement. Move it to AC5.1 or a constraints note; do not embed it in an AC that should be one sentence.
- **AC4.2** names the sidecar file (`excel-ingest-state.json`). Naming the file is an implementation detail, not a requirement. The requirement is: a persistent mapping from Excel row key → JSONL id. Cut the filename.

---

*Net verdict: the spec is close to tight. Two real cuts — AC3.1 verbosity and AC5.2 forward-language — and one constraint de-duplication. Everything else earns its keep.*
