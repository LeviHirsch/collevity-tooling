# Contrarian Review — JSONL Schema Spec (Revision 3)

_2026-06-24 | greenfield mode_

---

## Pass 1: Assumptions Made Explicit

- **"JSONL → SQLite → Postgres portability is real."** The Constraints section asserts a logical seam that abstracts the ladder. AC2.2 immediately breaks this: `edit_entry` "rewrites the line" for JSONL and becomes an `UPDATE` for Postgres. These are structurally different operations. The ladder is asserted, not designed.
- **"Read-time ingest is simpler than a daemon."** AC4.6 pipes ingest through `read_day` to avoid cron. This assumes coupling read and write paths carries no cost.
- **"Thin stream means no history on the raw entry."** DEC-009 defers revision and typing to strata. AC1.7 then defines `meta_notes` as an append-only prose string with ISO-timestamps — informal revision history on the raw entry itself.
- **"MDT-row identification is a runbook detail."** Open Questions calls it deferred; AC4.4 still lands it in Phase 2 as a deliverable. One of those is wrong.
- **"UUIDv7 is worth an external dependency."** AC1.2 flags `uuid6`/`uuid-utils` as a required build dep. The spec assumes temporal ordering via UUID matters, when `created_at` already carries ordering information.

## Pass 2: Inversions

- **Invert AC4.6 (read-time ingest):** `read_day` is a read operation. If it triggers `append_entry` / `edit_entry` as a side-effect, it is no longer idempotent as a read. Any consumer that calls `read_day` twice expecting stable output will see different results mid-migration. The "no daemon" benefit is real; the read/write coupling cost is not accounted for.
- **Invert AC2.2 (edit-in-place):** The spec excludes `modified`/`updated_at` (AC1.8, DEC-006) to keep the stream thin. But `edit_entry` with no audit trail means a corrected entry is indistinguishable from the original. If the trust model ever needs to distinguish "as-dropped" from "as-corrected," there is no recovery path — by design.
- **Invert the Excel-blind framing:** The Goal section says retiring Excel is motivation, not identity. But AC4 constitutes nearly half the leaf ACs. The spec may be solving Excel migration with a schema wrapper around it, not the other way around.

## Pass 3: Challenge the Problem Statement

What if the problem is capture friction, not storage shape? The spec fixes the tz mis-bucketing bug (AC3.2, DEC-014) and the Excel-ingest mess (AC4.*) — both are symptoms of the capture surface, not the store. A better store with the same capture surface still produces mis-timed, structurally thin entries. The spec assumes the store is the bottleneck.

## Pass 4: Biggest Risk

**AC4.6's read-time ingest makes `read_day` a write operation.** If that assumption is wrong — if any consumer treats `read_day` as a pure read — the seam contract breaks before Excel is retired, and the bridge cannot be safely deleted (AC4.5 premise collapses).
