# Contrarian Review — JSONL Schema Spec v001
> 2026-06-24 | greenfield mode

---

## Pass 1: Explicit Assumptions

- **"Append-only" is the right storage model** — The Goal names a "thin, append-only, horizontal time-stream," then AC2.2 immediately breaks it with edit-in-place line rewrites.
- **JSONL is a stepping stone, not a trap** — The spec assumes JSONL is safe to migrate away from because the seam abstracts it. But the Excel bridge (AC4.3) reads and rewrites individual lines by matching on timestamp — that is a raw JSONL-specific operation that leaks through the seam.
- **`/checkin` parity is a worthy constraint** — AC3.1 mandates matching `read_dropper_day.py` output exactly. That output format was designed around a 3-column Excel sheet with its own bugs. Parity preserves those bugs by definition.
- **The bridge is temporary** — AC4.6 makes ingest run "on-demand at read-time." That makes the bridge a permanent load-bearing consumer path, not a transitional script.
- **Thin-stream deferral reduces complexity** — Deferring `kind`, `entity_axis`, `tier`, and `occurred_at` to the strata layer (Out of Scope) means downstream consumers will need heuristics or re-parsing to answer even basic questions like "what kind of entry is this?"

---

## Pass 2: Inversions

- **What if edit-in-place is the wrong answer?** AC2.2 says rewrite the line; no revision. In a true append-only model, edits are tombstone + new entry. The current design says "logically portable up to Postgres" (DEC-005/AC2.3), but Postgres doesn't do line-rewrite — it does UPDATE. So the seam abstraction already breaks at its stated upgrade path.
- **What if `/checkin` parity should be cut?** AC3.1 exists to avoid breaking a downstream consumer while migrating. But if the bridge + sidecar (Phase 2) exists to transition off Excel, a cleaner path is: migrate first, then rebuild `/checkin` once against the new seam — not preserve a buggy interface as a contract.
- **What if JSONL → SQLite migration never happens?** The portability argument (DEC-005) is the justification for the seam's complexity. If the system stays JSONL, the seam is over-engineering. If migration is real, the on-demand read-time ingest (AC4.6) and edit-in-place (AC2.2) are both wrong primitives.

---

## Pass 3: Challenge the Problem Statement

The spec frames this as "replace Excel Dropper." But the real problem may be that the downstream consumer (`/checkin`) is too tightly coupled to a physical format. If the coupling were fixed at the consumer, no schema migration would be needed — the Excel rows could stay. The spec is solving an integration problem by moving the data, not by fixing the interface.

---

## Pass 4: Biggest Risk

**AC2.2 (edit-in-place) directly contradicts the append-only guarantee in the Goal and the portability promise in DEC-005/AC2.3.** If this assumption is wrong, the storage seam is not actually portable and the migration path to SQLite/Postgres requires a different edit primitive — invalidating the architecture's central claim.
