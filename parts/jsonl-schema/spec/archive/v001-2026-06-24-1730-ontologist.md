# Ontologist Critique — JSONL Schema Spec — Revision 3
*2026-06-24*

---

## 1. Essence

Strip the Excel framing and what remains is correct: a *write contract* — five required fields plus three seam functions (`append_entry` / `edit_entry` / `read_day`) that insulate downstream consumers from storage evolution. The Goal section names this explicitly ("the core store is permanent and Excel-blind; the bridge is scaffolding that gets deleted"). No symptom masquerading as a goal. Essence is sound.

## 2. Root cause

The root need — a durable, low-friction capture-to-context pipeline — is correctly distinguished from the transitional motivation (retiring Excel). One residual tension: the goal says "every pipeline part reads from and writes to" this store, but AC3.1 deliberately scopes `read_day` as v1's only read surface. That constraint is the right call, but the spec frames it as a seam property rather than a scaffolding boundary. If a downstream part later reads by tag or week, it won't extend the seam — it will violate it or wait for the seam to evolve. That boundary should be named as a v1 scope limit, not described as what the seam "is."

## 3. Prerequisites

AC1.2 names the `uuid6`/`uuid-utils` dependency explicitly — good. The load-bearing gap is the offset-correctness assumption (Constraints, DEC-017): "each capture surface stamps `created_at` with the correct local offset; this part assumes it and neither re-derives nor validates it." For Excel this is handled by the bridge; for the claude-hook shape, the surface hasn't been built yet and AC1.6 defers validation to hook go-live. No detection mechanism exists if a surface stamps incorrectly. Accepted risk, but worth naming explicitly as a future-surface onboarding obligation, not just a deferred spec item.

## 4. Hidden assumptions

AC4.6's on-demand ingest is the sharpest issue: `read_day` triggers bridge writes — a read operation with write side effects. The spec frames this as a cadence choice, but it silently violates the seam's read/write separation, complicates testing (a `read_day` call isn't idempotent during transition), and creates a subtle risk if `read_day` is called concurrently or from a context where writes aren't expected. The spec should call this out as a read-with-side-effect exception to the seam contract, scoped explicitly to the bridge's lifetime — not leave it implicit in the phrase "piggybacking."

## 5. Phase ordering

No forward-dep violations spotted. Phase 2 hooks into Phase 1's `read_day`; Phase 1 needs no knowledge of Phase 2.

---

**Most load-bearing concern:** AC4.6's side-effectful `read_day` — blurring the seam's read/write contract — deserves an explicit carve-out in AC2.3 or AC4.6 itself before implementation begins.
