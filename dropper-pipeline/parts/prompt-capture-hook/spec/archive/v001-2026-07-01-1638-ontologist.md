## 1. Essence
Unchanged from Rev 1: this is a telemetry tap, not a "capture" feature — pure plumbing that stamps and appends. Rev 2 doesn't drift from that essence; D1-D3 and AC4.3 are plumbing-adjacent (ordering, safety, diagnostics), not new capabilities. Good.

## 2. Root cause
Holds. One addition worth naming: AC4.3's error sidecar reframes "fail-open" from *invisible* failure to *discoverable* failure (DEC-009) — that's the correct root fix (a silent, permanent data-loss mode was the real symptom Rev 1 left unaddressed under AC4.1 alone).

## 3. Prerequisites — primary focus
**D1/D2/D3 typing is clean.** All three are described as things the hook *depends on*, not implements, and the "Out of scope" list explicitly disclaims implementing them. AC5.1 and the chronological-order constraint bullet correctly cite D1/D2 inline rather than smuggling them in as hook ACs. This is the right ontological move.

One gap: **D3 has no AC-side anchor.** D1 is cited by AC5.1, D2 is cited by the constraint bullet, but D3 (concurrent-append safety) is never referenced from AC3.1, even though AC3.1 is exactly the AC that would break if `append_entry` corrupted a line under concurrent writers. Either add a parenthetical to AC3.1 ("corruption under concurrent append is D3's guarantee, not this AC's") or note why it's intentionally silent — as written, a reader of AC3.1 alone wouldn't know the risk exists.

**Naming:** `read_day`, `append_entry`, `created_at` are used consistently with the rest of the spec. `sync_sources` and `_rewrite_all` appear only in D2 — can't cross-check against part-1 without that doc, but `_rewrite_all`'s leading underscore signals a private method. Naming a dependency contract against a private symbol is fragile: if part-1 renames/refactors it, D2's contract has no public seam to survive on.

## 4. Hidden assumptions — AC4.3
The error sidecar is a new entity with no defined identity: no path, filename, format, or rotation policy is given (contrast AC1.1, where the script's "stable path" is grounded by the settings.json reference). It doesn't collide with the lake — the boundary between "captured data" (lake) and "capture-failure diagnostics" (sidecar) is conceptually clean, and AC4.3's layering over AC4.1 (fail-open first, breadcrumb second, both swallow) is correctly MECE. But the spec assumes someone will define and monitor this file later with no lifecycle (unbounded growth, no reader named) — flag for the implementer, not necessarily a spec defect given Phase 1 scope.

## 5. Phase dependency invariant
No forward-dep violation: Phase 1 carries AC4.3 and all of AC1-AC4, correctly deferring only AC5.1's sub-minute ordering (D1) to Phase 2's verification note. Phasing is coherent.

**Most load-bearing concern:** AC3.1 should explicitly disclaim (or accept) the D3 concurrency gap the way AC5.1 discloses D1 — right now a reader could mistake AC3.1 as fully satisfied pre-D1/D3.
