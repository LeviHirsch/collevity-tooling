# Contrarian Review — Revision 2 (fresh pass on Cross-part deps + AC4.3)

## 1. Assumptions made explicit

- **"Built and installed independently" (Cross-part deps intro) assumes independence means "compiles/runs," not "produces correct data."** The hook ships stamping sub-minute `created_at` (AC2.2) into a lake whose `read_day` (D1) still sorts by `HH:MM` string. That's not independence — it's writing precision the reader silently discards. Anyone using `read_day` output today gets same-minute entries in arbitrary/undefined order and no signal that ordering is unreliable.
- **D2 assumes the unsorted "transient live tail" is harmless.** It isn't scoped: between syncs (which could be days, given DEC-005's global/all-day capture), any consumer reading the raw file directly — not just `read_day` — sees a non-chronological tail with no marker of where sorted-vs-tail begins.
- **D3 is graded as a hardening nice-to-have, but the spec's own text ("global scope makes concurrent Claude sessions realistic") admits this is not hypothetical.** iCloud sync + no lock + realistic concurrency = a live corruption/data-loss risk that exists the moment this hook is installed, independent of whether part-1 iteration 2 ever happens.

## 2. Invert the assumptions

Invert "defer D1/D2/D3 to a future part-1 iteration": what if instead the hook's install is gated on D3 landing first? The spec treats D3 as optional hardening; inverted, D3 is a precondition for safely turning on global scope at all, because the failure mode (silent lake corruption under iCloud) is unbounded and worse than any capture loss AC4 protects against. Shipping the hook without D3 optimizes for the wrong side of the risk.

## 3. Challenge the problem/AC4.3

AC4.3's "best-effort" qualifier is not a testable acceptance criterion — it's an admission that the requirement can fail and still pass review. A real AC states the guaranteed behavior (hook never blocks) and separately owns the *known* gap (sidecar may also fail) as a documented limitation, not folded into the AC's own wording. As written, "both writes fail → capture vanishes, zero trace" is buried inside the AC rather than surfaced as an accepted risk in Constraints/Out-of-scope. The sidecar itself has no rotation/read path defined — it can grow forever, unread, becoming exactly the kind of orphaned artifact DEC-009's "discoverable" goal was meant to prevent.

## 4. Biggest risk

If D3 is wrong — i.e., iCloud-backed concurrent appends are *not* safe today — then installing this hook globally (before any part-1 fix ships) risks silently corrupting or truncating the live lake the first time two Claude sessions submit prompts near-simultaneously, and the spec currently treats that as someone else's future problem rather than a launch blocker.
