# Ontologist critique — prompt-capture-hook spec v001

## 1. Essence
What this *is*: a single deterministic write — stdin field → `append_entry` call — wrapped in a try/except that always exits 0. The Goal line ("Install a global Claude Code `UserPromptSubmit` hook that appends every user prompt to the Collevity live lake") names this correctly; it does not inflate into a feature description. The essence holds up under the AC tree too — AC1–AC5 are all facets of "one fail-open write," not a creeping feature list. No essence drift found.

## 2. Root cause
The stated goal is a root need, not a symptom — but only because DEC-002 deliberately defers the symptom-adjacent question ("which prompts are worth keeping?") to a later triage layer. If you squint, the *real* underlying need is "Levi wants the shape of his attention over time visible without manual logging," and this spec satisfies exactly the capture half of that, leaving the read/value half (triage, contextualize) explicitly out of scope. That's a coherent split, not scope-creep avoidance — DEC-002's rationale ("the timestamped flow... is itself valuable data... independent of any single prompt being a keeper") names the deeper formulation correctly. No symptom-masquerading found.

## 3. Prerequisites
Two load-bearing prerequisites are flagged by the spec itself as open (Open Questions 3–4) rather than hidden: script language/path, and `collevity` package resolution + `COLLEVITY_LAKE` env for the hook's execution context. These are real gaps, properly surfaced rather than smuggled in as assumptions — good. One *unflagged* prerequisite: AC2.2 assumes the host machine's local clock/offset is correct at capture time. The spec inherits this from part-1 DEC-017 ("offset correctness is owned at capture") but never states the hook trusts the OS clock with no drift/DST-transition check. Probably fine to leave unstated given DEC-017's existing precedent, but worth one line acknowledging it's inherited, not re-decided.

## 4. Hidden assumptions
- Assumes `UserPromptSubmit` fires once per literal user submission, not also for hook-internal/programmatic resubmissions. If a future Claude Code version reinvokes the hook on retries, AC3.1's "exactly one new JSONL line per prompt" could silently double-write. Not addressed.
- Assumes `session_id` is stable and present for *every* invocation context (including resumed sessions, background agents). If a future SDK path lacks `session_id` on stdin, AC2.5's "non-empty session_id" becomes unsatisfiable and AC4.1's fail-open swallows it silently — acceptable per design, but means a structural gap could go unnoticed indefinitely since nothing surfaces it.
- Open Question 2's caveat ("echo raw stdin once to confirm key names") is itself an assumption-check baked into the rollout — good practice, but note it's a one-time manual verification, not a regression guard if Claude Code changes the payload shape later.

## 5. Phase dependency invariant
Phase 1 carries the entire write path (AC1–AC4) and is buildable/testable without Phase 2. Phase 2 (AC5.1) depends only on a live installation, not on any Phase-2-only capability Phase 1 silently borrows. Phase ordering: no forward-dep violations spotted.

## Most load-bearing concern
The unaddressed re-invocation/idempotency assumption (point 4, first bullet) is the one most worth a deliberate decision — AC3.1 asserts "exactly one line per prompt," but nothing in the spec defends that count against double-fires from retries or future hook semantics changes.
