# Ontologist review — prompt-capture-hook spec (v001, 2026-07-13)

## 1. Essence
What this *is*: an arrival-order write beam from Claude Code's prompt-submit event into the lake — nothing else. The Goal section states exactly that ("deterministic, fail-open, no LLM in the path") and every AC group (install/payload/persistence/fail-open/readability) is a direct decomposition of "get the byte in, don't break the session." No feature creep masquerading as goal — Out of scope explicitly amputates triage, contextualize, and thread-discrimination. This is a clean, minimal-essence spec.

## 2. Root cause
The stated goal is a genuine root need, not a symptom: without unattended raw capture, the rest of Dropper (triage, strata, thread) has nothing to operate on. The spec resists the temptation to solve triage or semantic clustering here (DEC-002, DEC-004) — correctly recognizing those are downstream needs with different failure tolerances (this layer must never block; triage can be lossy-slow). No deeper reformulation needed.

## 3. Prerequisites
Two load-bearing assumptions are named and resolved (part-1 schema shape, hook stdin contract). One is **not** surfaced anywhere: AC1.1 says settings.json "contains a `UserPromptSubmit` hook entry" but never addresses composability — what happens if Levi (or a future tool) already has a `UserPromptSubmit` hook registered? Claude Code's hooks array can hold multiple entries per event; nothing in AC1 or INSTALL.md (per the spec's own cross-reference) states whether this hook must coexist with, replace, or be the sole entry. If a second hook is added later without this spec's awareness, does its installation instructions still apply cleanly? Worth one line.

## 4. Hidden assumptions
The fail-open constraint ("a lake-write failure must never delay or block prompt submission") is asserted but only tested against *failure* (AC4.1: exceptions → exit 0). Nothing in AC4 addresses **hang** rather than failure — e.g., a stalled iCloud filesystem write with no raised exception, just latency. Constraints call out iCloud multi-machine conflict-copies (DEC-016) as a known iCloud quirk, but not iCloud I/O latency as a blocking risk on the *same* machine. If the opposite of "writes fail fast or succeed fast" were true, the "never delay" guarantee in Success Criteria would be silently violated with no AC catching it. A timeout wrapper (or an explicit note that Python subprocess hooks are async from Claude Code's perspective, making this moot) would close the gap — but the assumption should at least be named as accepted risk if it isn't already implicitly true by hook execution model.

## 5. Phase dependency invariant
Phase ordering: no forward-dep violations spotted. Phase 1 carries all install/payload/persistence/fail-open ACs; Phase 2's AC5.1 depends only on Phase-1 output plus already-landed D1 — no backward reference.

**Most load-bearing concern:** whether the "never delay" fail-open guarantee is actually enforced against a *hang* (not just a raised exception) — confirm the hook's execution model is fire-and-forget/async from Claude Code's perspective, or add a timeout.
