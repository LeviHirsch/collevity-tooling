# Contrarian review — Rev 4, prompt-capture-hook spec

## 1. Assumptions surfaced

- **A. Timeout-kill = non-blocking, verified.** DEC-018 relies on "a non-2 exit (including a signal-kill) is non-blocking," but the same bullet admits "Claude Code's docs are silent on whether a *timeout* is specifically treated as blocking." The fix rests on an assumption the spec itself flags as unconfirmed.
- **B. The timeout's actual value is bounded and known.** AC1.1 only requires "an explicit bounded timeout" — no number appears anywhere in spec.md (DEC-018 mentions Claude Code's 30s *default* only as context, not as the chosen value). "Modest" is undefined. As written, an implementer setting 120s still satisfies AC1.1's letter.
- **C. A SIGKILL mid-append is equivalent to a swallowed exception.** AC4.1 treats any non-2 exit "including a signal-kill" as safely fail-open, identical in effect to a caught I/O error. But AC3.1's line-integrity guarantee (D3) covers *concurrent multi-process* races via flock — not a *single writer killed mid-`os.write()`*. A torn write is a different failure class than a contended lock.
- **D. Timeout margin comfortably exceeds nominal runtime.** Nominal path = `.venv` python startup + `import collevity` + D3 flock acquisition + iCloud file materialization. No AC establishes that this nominal path reliably finishes well under the timeout, only that *worst case* is bounded.

## 2. Inversions

- If (A) is false and a timeout-kill is actually blocking on some Claude Code version, the fail-open guarantee breaks silently in exactly the stall scenario Rev 4 exists to fix — and no AC would catch it (Success criteria only simulate a read-only-path *exception*, never a *stall-to-timeout*).
- If (C) is false — a kill mid-`write()` leaves a torn/partial JSONL line — the blast radius is worse than "one capture dropped to breadcrumb" (the Constraints framing): a torn line can break `validate()`/parsing for the whole file on the next `read_day`, contradicting AC3.1's "parseable as a valid JSON object" guarantee.
- If (D) is false under real iCloud contention (which DEC-016/D3 already acknowledge as a live pressure), the "modest" timeout fires on *routine* prompts, not just genuine stalls — quietly degrading capture rate under ordinary conditions rather than only in the rare-stall case DEC-018 targets.

## 3. Problem-statement challenge

Rev 4 declares the stall gap closed by *adding* a timeout, but no AC exercises the timeout path itself — none simulates "append stalls past the bound → process is killed → prompt still proceeds → lake file is still valid." Success criteria test exception-based failure (read-only path) and nominal success, not the kill path this revision introduces. The mechanism added to close the prior gap is itself unverified by the spec's own AC set.

## 4. Biggest risk

If a timeout-kill can land mid-write and leave a torn JSONL line, DEC-018 trades a "prompt delayed" failure mode for a "lake corrupted" failure mode — strictly worse than what it replaced — and nothing in AC3 or AC4 would detect it.
