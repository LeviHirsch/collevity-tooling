# Contrarian Critique — Prompt-Capture Hook v001

## 1. Assumptions made explicit

- **"Every prompt is worth capturing" (DEC-002, Goal).** Maybe most prompts are noise and only a fraction carry thread-signal — capturing all of them just inflates the lake the triage layer (deferred, not yet built) will have to dig through later.
- **"Global scope is reversible" (DEC-005).** The decision log claims narrowing later is "reversible and lossless," but it's reversible only for *future* writes — every prompt captured during the over-broad window (including outside Collevity work) is permanent, including unrelated client/personal sessions. That's not lossless, it's a one-way ratchet on what's already in the lake.
- **"The hook is the right place to own offset-correctness" (Constraints).** Spec assumes the *hook's* local clock is authoritative. What if the host machine's clock/timezone is wrong at capture time (stale VM, travel, DST edge)? Nothing in AC2.2 guards against a wrong-but-well-formed offset — it only checks the string is ISO-8601 with *a* matching offset, not that the offset is *correct* for the user's actual location.
- **"Fail silently is the same as fail-open" (AC4.1).** The spec equates "never block the prompt" with "swallow and discard the error." It assumes silent data loss is an acceptable cost of fail-open, with no logging/telemetry path mentioned anywhere — not even out-of-scope explicitly disclaims it.

## 2. Inversions

- Invert DEC-002: **what if not everything should go?** A trivial allow-nothing skip-list (e.g., `/`-prefixed slash commands) was explicitly deferred as "itself triage" — but a one-line denylist isn't triage, it's noise reduction, and costs nothing extra in v1.
- Invert "global is safer than workspace-scoped" (DEC-005): what if global capture of *every* Claude Code session (including unrelated codebases/clients) creates a privacy/scope-creep problem the spec never names as a risk, only as a migration convenience?

## 3. Challenge the problem statement

- What would happen if the team did **nothing** here, and just relied on existing session transcripts (which Claude Code already persists) instead of building a parallel capture pipeline? The spec never argues why `append_entry`-mediated capture is better than mining existing session logs after the fact.
- AC5.1 ties success to `read_day` surfacing entries "with the correct local wall-clock time" — but no AC ever defines what happens when two hooks fire from concurrent sessions at the same wall-clock minute. Is collision a non-problem, or untested?

## 4. Biggest risk

If DEC-005's claim that global-then-narrow is "lossless" is wrong — i.e., if early indiscriminate capture creates a clutter/privacy debt that can't be cleanly pruned later — the entire v1 scope decision (and the AC tree built on top of it) is the wrong starting point.
