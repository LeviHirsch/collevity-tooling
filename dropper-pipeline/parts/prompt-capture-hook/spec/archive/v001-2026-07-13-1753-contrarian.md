# Contrarian Review — prompt-capture-hook spec.md (2026-07-13)

## 1. Assumptions surfaced
- **AC4.1 assumes failure = exception.** It enumerates I/O error, validation error, import error, missing env var — all things that *throw*. It never names a hang/stall (e.g. iCloud lake path mid-sync, NFS-style stall on `append_entry`). "Non-blocking" in Constraints is a latency claim; AC4.1 only tests a correctness claim (exit 0, empty stdout). Nothing pins down a timeout.
- **AC3.1 assumes single-fire.** It names the double-fire case ("if Claude Code ever fires the hook more than once") and waves it off as DEC-002/010 triage debt — but no AC actually observes whether double-fire happens under real Claude Code versions. This is an untested empirical claim wearing the clothes of a resolved decision.
- **AC2.1 assumes "verbatim" has no edge case.** No AC addresses pathological input: multi-MB pastes, embedded control/null bytes, or prompts containing secrets pasted from client work (relevant given DEC-005's global scope). "No truncation, no escaping artifacts" is asserted, not bounded.

## 2. Inversions
- Invert "fail-open is the prioritized guarantee" (DEC-017): for a *personal capture* tool, a rare visible failure might beat invisible, permanent loss — the user could notice and re-paste. The spec never asks whether occasional friction is cheaper than silent gaps in the record it's built to be complete. No AC measures how often the sidecar actually catches what fail-open swallows, so the real loss rate is unmeasured, not just accepted.
- Invert "capture everything, filter later" (DEC-002 held): global scope means client/sensitive prompts sit in the personal lake indefinitely before any triage exists. What if triage should gate *before* persistence for this one dimension (confidentiality), rather than after? The spec treats this purely as a timing tradeoff (DEC-014), never as a possible one-way door (leaked client content can't be un-persisted from backups/sync history even if later deleted from the lake).

## 3. Problem statement challenge
- Does Claude Code already retain session transcripts containing the same prompt text? If so, this hook may be duplicating an already-recoverable source rather than capturing something that would otherwise be lost. The spec never states why transcript-mining was rejected in favor of a live hook — an omission, not a resolved question.

## 4. Biggest risk
If `append_entry` can stall (not throw) on a synced/locked lake path, AC4.1 as written would pass tests while the live constraint ("must never delay... prompt submission") silently fails in production — the one failure mode most plausible given DEC-016's iCloud conflict-copy risk is exactly the one no AC exercises.
