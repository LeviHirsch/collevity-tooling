# Ontologist Review — JSONL Schema Spec — Revision 2
*Date: 2026-06-24*

---

## 1. Essence

The spec correctly strips its own surface feature: the Goal section explicitly names "retiring Excel" as scaffolding, not identity. What remains is a field-level contract + thin access seam over a single-author append-dominant time-stream. That's accurate. The stated goal IS the essence here.

No issue.

---

## 2. Root cause

The root need is a durable, portable, queryable capture stream. The spec serves that directly rather than describing a symptom. AC3.1's "output-format parity, not behavioral replication" framing is the right call — it resists the trap of encoding the old tool's bugs as requirements.

No issue.

---

## 3. Prerequisites

Two unstated dependencies:

**UUIDv7 library.** AC1.2 and AC2.1 require UUIDv7-string generation. Python's stdlib `uuid` has no v7 support; an external package (`uuid6`, `uuid-utils`, or similar) is required but unnamed. This is a build dependency, not a minor detail — an implementer hitting this cold will be blocked.

**MDT-row identification.** Open Question 1 is flagged as "does not block sealing the spec," but AC4.4 cannot be implemented without it. It is a prerequisite for Phase 2, not a migration-runbook detail. Deferring the *mechanism* while marking Phase 2 complete-able is inconsistent with the phase invariant's intent. The question should be promoted to a Phase 2 blocker or the AC should explicitly scope to EDT-only with MDT as a follow-on.

---

## 4. Hidden assumptions

**Capture surface correctness is load-bearing but out of scope.** AC1.3 and AC3.2 together guarantee correct local-day bucketing — but only if the capture surface stamps `created_at` with the correct local offset at write time. Capture surfaces are explicitly out of scope (§ Out of scope). The spec cannot enforce this guarantee. If a surface writes UTC or a wrong offset, AC3.2 silently produces wrong bucketing with no detection path. This assumption should be surfaced, even if the mitigation is simply "each capture-surface spec is responsible for offset correctness."

**On-demand ingest assumes `read_day` is the only consumer entry point.** AC4.6 relies on piggybacking ingest onto `read_day` calls. This holds only if every consumer path goes through `read_day`. The spec does not prohibit a consumer from reading the JSONL directly (AC2.3 forbids scattered raw writes, not reads from non-seam callers).

---

## 5. Phase ordering

Phase 2 depends on `read_day` (AC3.1, AC3.2) which lands in Phase 1. No forward-dep violations spotted.

---

**Most load-bearing concern:** the correctness of `created_at` offset is the foundation of AC3.2's bucketing guarantee, yet responsibility for stamping the correct offset lives entirely in out-of-scope capture surfaces — the spec should name that dependency explicitly rather than leaving it implicit.
