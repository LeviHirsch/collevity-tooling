# Ontologist Review — JSONL Schema Spec — Revision 4
**Date:** 2026-06-24
**Reviewer:** Ontologist persona
**Spec revision under review:** 4 (greenfield, phase: revised)

---

## 1. Essence

The spec is correctly identified as a *storage seam with a field contract*, not a capture surface or query engine. That framing holds up. What it IS: a canonical entry shape plus four named ops that gate all reads and writes. The Goal section earns this — "thin, append-dominant, horizontal time-stream" is precise and not feature-level. No issue here.

## 2. Root cause

The stated goal is sound at root: the problem is that entry data is currently trapped in a format-coupled store (Excel), and the fix is a format-agnostic entry contract accessed only through a thin seam. That is the root need, not a symptom. The "retiring Excel" framing is correctly demoted to motivation in the Goal paragraph.

One soft concern: success criterion (b) — "`/checkin` reading JSONL via `read_day` matches Excel-era output" — frames parity with `read_dropper_day.py` as a success criterion. If the existing behavior was wrong (tz mis-bucketing, per AC3.2), "matches" is the wrong target for correctness. AC3.1 clarifies "output-format parity, not behavioral replication," but this tension should be made explicit in the criterion itself, not only in the AC.

## 3. Prerequisites

The spec has one load-bearing unstated dependency: the `sync_sources` seam (AC5) must be callable by consumers *before* `read_day`, but the spec nowhere specifies who owns the call site. AC5.1 says "a consumer needing fresh data composes `sync_sources()` then `read_day()`" and labels it an "op-path concern" out of scope. That's a reasonable deferral — but it creates a gap: any consumer that calls `read_day` without calling `sync_sources` first will silently get stale data with no error. The seam contract doesn't say whether staleness is surfaced. If the only consumer in v1 is `/checkin`, the burden is on `/checkin` to know to compose — nothing in this spec enforces it. This assumption is load-bearing and unstated.

## 4. Hidden assumptions

**Assumption A — sidecar timestamp keying is stable:** AC4.2 keys the sidecar on "drop-timestamp, sub-second tiebreaker by row index." This assumes Excel timestamps are stable across re-opens and format conversions. Excel datetime cells can silently drift (float representation rounding) across saves or xls→xlsx round-trips. If timestamps shift, the sidecar key no longer matches, and the bridge silently creates duplicates instead of updating. The spec should either acknowledge this or specify a tie-breaker that is more stable than floating-point datetime.

**Assumption B — `sync_sources` extensibility is additive:** AC5.2 defers the multi-source registry but claims a second pull source "plugs in additively." This is asserted, not demonstrated. The spec defines no interface contract for ingesters — no signature, no error protocol, no freshness indicator — so the claim of plug-in additivity is untested. The abstraction names the home but doesn't sketch the boundary enough to validate it.

**Assumption C — offset correctness at capture surfaces:** The spec defers offset correctness to each surface (Constraints, DEC-017). This is structurally sound but assumes the claude-hook surface (reserved, AC1.6) will be built with this requirement in mind. It's a reasonable assumption for a spec that explicitly marks hook as reserved — just worth naming.

## 5. Phase ordering

Phase ordering: no forward-dep violations spotted. AC5.1 (`sync_sources` boundary, no ingesters) is correctly in Phase 1; AC5.2 (Excel registered as sole v1 ingester) correctly in Phase 2. Phase 2's `Depends on` clause is accurate.

---

**Most load-bearing concern:** The `sync_sources` composition contract (Q3) — the spec defers who calls `sync_sources` as an "op-path concern," but leaves no mechanism to prevent a consumer from getting silently stale data; this gap will bite at the first `/checkin` integration and should be resolved before implementation begins.
