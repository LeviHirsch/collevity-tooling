Reviewer: ontologist persona

## 1. Essence

The spec's stated goal is "define the canonical field-level shape of a Collevity entry and the thin storage seam that enforces it." Strip the Excel context and the pipeline scaffolding: what remains is a *durable identity contract* — a minimal schema plus four seam ops that give every downstream system a stable surface to stand on. That is the right level of abstraction. The goal statement captures it.

No concern.

## 2. Root cause

The underlying need is that raw capture — across surfaces, across time — must land in one addressable, retrievable pool without loss, and `/checkin` must be able to read from it. The spec satisfies that directly, not via a surrogate. Retiring Excel is correctly called out as *motivation*, not identity.

No concern.

## 3. Prerequisites

One prerequisite is unstated in a potentially load-bearing way: **the Python `uuid6` / `uuid-utils` build dependency** is noted in AC1.2's parenthetical, but it does not appear in any out-of-scope declaration, constraint, or phase deliverable list — the implementer needs to know it must be available before Phase 1 is runnable. The note buries it inside an AC. It should surface as an explicit build dependency in Phase 1 or in Constraints. Minor, but concrete.

Everything else — iCloud local filesystem access, IANA zone deferral, single-user assumption, no daemon — is either named in Constraints or covered by decisions.

## 4. Hidden assumptions

Two assumptions survive all four prior rounds:

**A. Col-E timestamp stability across Excel saves (AC4.2)** is flagged parenthetically and backed by DEC-016, but the spec offers no failure behavior if it is violated — beyond "fails loudly." What loud failure looks like (exception? corrupt sidecar? orphaned entries?) is not specified. This is the only place where a violated assumption could produce silent data divergence rather than an abort. Worth one sentence naming the observable failure mode.

**B. The `/checkin` consumer owns the `sync_sources → read_day` composition.** DEC-019 and AC5.1 state this as a contract; the consumer is named. The assumption is that no *other* tool (a future quick-query helper, a stats script) will call `read_day` directly and silently read stale data. Since v1 has exactly one consumer, this is acceptable risk — but the spec could note "any future consumer must observe this composition" in AC5.1 to make the invariant explicit rather than implicit.

Neither rises to load-bearing for this part alone; both are named rather than hidden.

## 5. Phase ordering

Phase 1 delivers `sync_sources` as a boundary with no ingesters; Phase 2 registers the Excel bridge as its sole v1 ingester. AC4.6 references `sync_sources` (AC5) as already defined. AC5.1 is correctly assigned to Phase 1. Phase 2 adds AC5.2 (exactly one ingester).

Phase ordering: no forward-dep violations spotted.

**Most load-bearing item for the author:** The `uuid6` / `uuid-utils` build dependency buried in AC1.2's parenthetical should be promoted to an explicit named prerequisite in Phase 1 — it is the only external dependency that can silently block Phase 1 from running at all.
