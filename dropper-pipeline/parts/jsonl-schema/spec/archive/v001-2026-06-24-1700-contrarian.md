# Contrarian Review — JSONL Schema Spec (Revision 2)

## Pass 1: Assumptions Made Explicit

1. JSONL is a viable long-term physical store (Constraints, AC2.3).
2. A three-function seam (`append_entry` / `edit_entry` / `read_day`) is the right abstraction boundary.
3. The thin-stream principle is correct — structure belongs downstream (Constraints, DEC-009).
4. The Excel bridge deserves a live-channel path, not a one-shot dump.
5. Edit-in-place with no revision history is acceptable (AC2.2, DEC-006).
6. The 852 rows are worth idempotent migration rather than a clean-cut import.

## Pass 2: Inversions

**JSONL as long-term store.** The seam exists to paper over JSONL's edit problem: rewriting a line in a growing file is fragile, and the spec acknowledges the ladder to SQLite/Postgres. If that move is likely, JSONL is a poor starting point — it forces a physical `edit_entry` that differs from the logical one at every tier, making AC2.3's "storage-agnostic" claim immediately hollow.

**Thin-stream principle.** If every consumer re-derives `kind`, `entity_axis`, and temporal context from raw `text`, the cost isn't eliminated — it's deferred to ingest, likely repeatedly. The `/checkin` skill already expects structured output. The spec defers structure but never shows where or when it arrives.

**`read_day` in the seam.** AC3.1 bakes a day-bucketing view into the storage abstraction. That is not a storage primitive — it's a query. The claim that the seam is "storage-agnostic up the ladder" (AC2.3) is undermined the moment any consumer needs `read_week`, `read_by_tag`, or any read shape the spec didn't anticipate. The seam already leaks view logic on day one.

**Bridge as live channel.** AC4.6 mandates on-demand read-time ingest (every `read_day` call triggers an Excel parse). A one-time migration plus manual drop from switch-day would be simpler and retire the bridge sooner. The live-channel framing increases coupling for a path destined for deletion.

**No revision history.** AC2.2 says no lineage. AC4.2–AC4.3 require a sidecar snapshot to detect text changes across ingest runs. The spec *has* revision tracking — it just lives in `excel-ingest-state.json` and sits outside the schema. That's not "no revision history"; it's revision history without integrity guarantees.

## Pass 3: Challenge the Problem Statement

AC4 (six criteria) consumes more spec surface than AC1 (the schema itself). If "the bridge is scaffolding that gets deleted," why does it dominate? The spec's center of gravity is the transition, not the store. The transition is eating the identity the Goal section explicitly tries to protect.

## Pass 4: Biggest Risk

`read_day` embedded in the storage seam (AC3.1) is a view concern masquerading as a storage primitive. It will force a seam redesign as soon as any consumer needs a read shape the spec did not anticipate — and that moment arrives before the Excel bridge is even retired.
