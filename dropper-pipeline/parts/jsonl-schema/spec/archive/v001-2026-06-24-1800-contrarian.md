# Contrarian Review — Revision 4
> Spec: Collevity Entry Store — JSONL Schema
> Reviewer: Contrarian persona
> Date: 2026-06-24

---

## Pass 1: Assumptions made explicit

- **"A storage seam is necessary."** The spec treats `append_entry / edit_entry / read_day / sync_sources` as self-evidently the right shape. It assumes four operations is the right granularity and that a seam is better than direct file access.
- **"Pull sources always need a coordination op."** AC5.1 asserts that pull-based sources require `sync_sources` before reads. This assumes the pull-pull pattern is categorically different from push, when in practice the line is blurry (what if the mobile cache does its own push on connect?).
- **"UUIDv7 is the right id strategy."** AC1.2 treats this as decided. It introduces an external dependency to fix a problem (`uuid6`/`uuid-utils`) that a simpler ordered id (timestamp + counter) would also solve.
- **"The schema must be storage-agnostic up the JSONL → SQLite → Postgres ladder."** The constraints section asserts this portability requirement. But v1 is single-user/local; migration to Postgres is speculative. The abstraction cost is paid now for a future that may never arrive.
- **"`sync_sources` is permanent."** The Constraints section declares it "a permanent seam." Permanence is asserted, not argued.

---

## Pass 2: Inversions

- **Invert the seam.** What if raw JSONL file access is fine for v1, and the seam is premature? For a single-user local store with one consumer (`/checkin`), a thin wrapper buys swappability at the cost of complexity. The seam abstraction could be Phase 2, introduced only when a second consumer or second backend appears.
- **Invert `sync_sources` permanence.** What if `sync_sources` is *only* a transitional scaffold, not permanent? If push surfaces eventually dominate and Excel retires, the pull-sync coordination op becomes vestigial. Calling it permanent locks the seam shape prematurely.
- **Invert UUIDv7.** A monotonic local id (e.g. `{unix_ms}-{counter}`) is sortable, stdlib-only, and human-readable enough to debug. Adding `uuid6`/`uuid-utils` as a build dependency for a local Python script is overhead whose benefit (global uniqueness, spec-compliance) does not pay off at single-user scale.
- **Invert the Excel-blind constraint.** "The schema is designed as if Excel does not exist" is a design ideal that adds complexity: a sidecar state file (AC4.2), explicit ignore-rules (AC4.1), a registered-ingester pattern (AC4.6). What if the bridge were just a one-shot migration script, not a live ingester? If the goal is to retire Excel, running the bridge once and cutting over is simpler than maintaining bidirectional sync indefinitely.

---

## Pass 3: Challenge the problem statement

The spec's goal is a "thin storage seam" for a "permanent" horizontal time-stream. But what problem does the seam solve that direct JSONL reads don't? The only concrete consumer named is `/checkin`. If `/checkin` reads one day's entries, it could do so with a three-line file read. The seam solves a future-proofing problem (swappable backends, multiple consumers) — not the stated v1 problem (retiring Excel and feeding `/checkin`).

What if we did nothing — kept Excel, kept `read_dropper_day.py`? The existing system already feeds `/checkin`. The pain point (tz mis-bucketing, DEC-014) could be patched directly in `read_dropper_day.py` without a new store. The spec treats Excel retirement as motivation, then explicitly says the store is "Excel-blind" and "permanent." Those two framings are in tension: if the store is Excel-blind and permanent, Excel retirement is incidental. If Excel retirement is the real goal, the store is transitional scaffolding dressed as infrastructure.

---

## Pass 4: Biggest risk

**AC5.2's "additively plugs in without redesigning the seam" promise is untested and unfalsifiable in v1** — with exactly one registered ingester and no second pull source in scope, the multi-source registry is purely speculative. If the seam shape turns out wrong for a second source (e.g. offline mobile with pre-assigned ids), v1's "permanent" seam will need redesign anyway, having paid the abstraction cost for nothing.
