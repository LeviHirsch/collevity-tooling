# Contrarian Review — JSONL Schema Spec — Revision 5
> Convergence check. Pass 4 (greenfield mode).
> Date: 2026-06-24

---

## Pass 1. Assumptions made explicit

1. **The seam is the right abstraction boundary.** The spec assumes `append_entry / edit_entry / read_day / sync_sources` is where abstraction should live. This is only safe if all consumers are known and stable.
2. **`/checkin` is the primary read consumer.** AC5.1 explicitly scopes v1 consumer composition to `/checkin`. The spec treats this as sufficient.
3. **Single-user, local, private is a permanent constraint** — not a phase constraint. All durability and concurrency tradeoffs rest on this.
4. **The 852-row count is stable.** AC4.3–4.4 assume a bounded, well-understood dataset.
5. **Excel col-E timestamp stability is a safe tiebreaker key** (AC4.2, DEC-016). This assumption is stated but its failure mode is "fails loudly" — which is correct but not tested by the spec itself.

---

## Pass 2. Inversions

1. **Invert assumption 1.** What if `/checkin` is the *only* near-term consumer and there is no second consumer within the life of this schema? Then the seam is over-engineered relative to a direct read-and-parse. The spec has deliberately decided this (DEC-005, DEC-018), and the cost is low — no new information changes this. Move on.

2. **Invert assumption 2.** What if a second read consumer emerges *before* the seam is complete — e.g., a weekly-report script reads raw JSONL directly to ship faster? The spec prohibits this (AC2.3: "no scattered raw file reads"), but enforcement is convention only. There is no test AC that verifies a consumer *cannot* bypass the seam. This is a gap: the spec says what must be true but provides no verification path for the constraint.

3. **Invert assumption 3.** What if a second local user (or a sync service like iCloud conflict resolution) writes to the JSONL simultaneously? Single-user is assumed but iCloud Drive — the apparent storage location — does not guarantee single-writer. A concurrent iCloud sync during an `append_entry` call could corrupt the append tail. Not in scope to solve, but not acknowledged as a risk.

---

## Pass 3. Challenge the problem statement

**AC1.7** specifies `meta_notes` as a "convention, not a validated constraint" (append-only, ISO-timestamp prefix, newest-at-bottom). Conventions without enforcement degrade. At rev 5, with no test AC verifying the convention, this field will accumulate malformed entries the moment a second writing surface exists. The spec could either (a) promote it to a validated format, or (b) explicitly document that it is unstructured prose and drop the convention framing. The current middle ground — a documented convention with no enforcement — is the most fragile option.

**Open Question 1 (MDT identification)** is correctly deferred, but AC4.4 says "the Phase-2 deliverable is the EDT stamping + backfill machinery" while the mechanism for identifying MDT rows is unresolved. This means Phase 2 cannot be marked complete until OQ1 is resolved. The spec does not say who resolves OQ1 or when — it just says "does not block sealing the spec." That's fine for sealing, but Phase 2 has a hidden blocker that should be surfaced in the phase description, not only in Open Questions.

---

## Pass 4. Biggest risk

**The seam-bypass risk (Pass 2, inversion 2).** AC2.3 prohibits scattered raw reads/writes but offers no verifiable enforcement. If any consumer — even a one-off script — bypasses `read_day` and reads JSONL directly before the migration to SQLite, the "logically portable" guarantee (Constraints, third bullet) is silently broken with no detection. This is the single assumption that, if wrong, most undermines the architecture.

---

*Overall: the spec is sound for convergence. The two actionable items are (1) add a test AC or documentation note for seam-bypass detection, and (2) surface OQ1 as a named Phase-2 prerequisite, not only a trailing open question.*
